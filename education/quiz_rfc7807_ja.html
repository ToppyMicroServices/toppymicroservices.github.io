Q1: JSONのProblem Details responseのmedia typeはどれ

Multiple Choice
**Explanation:** RFC 7807 Section 6.1は,JSON encodingだけでなくProblem Detailsとしての意味もrecipientが識別できるよう,`application/problem+json`を登録しています.単なる`application/json`はserializationしか示しません.Section 6.2はXML向けに`application/problem+xml`を別途登録しています. A: 汎用JSONとして処理できますが, payloadがProblem Details vocabularyに従うことをmedia typeで示せません. B: RFC 7807がJSON Problem Details用に登録したdedicated media typeです. C: `text/problem+json`はRFC 7807で登録されていません.

Q2: Problem Details objectの標準memberはどれ (複数選択)

Multi-Select
**Explanation:** RFC 7807 Section 3.1は`type`,`title`,`status`,`detail`,`instance`を標準memberとして定義します.Section 3.2はproblem type固有のextension memberを許しますが,`stackTrace`は標準memberではなく,使うならproblem typeの定義で明示する必要があります.未知のextensionは無視します. A: typeはURI referenceでproblem typeを識別します. B: titleはproblem typeの短いhuman-readable summaryです. C: statusはこの発生事象についてorigin serverが生成したHTTP status codeです. D: detailはこの発生事象に固有のhuman-readable explanationです. E: instanceは個別の発生事象を識別するURI referenceです. F: stackTraceは標準memberではなく, 実装内部の情報を露出させるおそれもあります.

Q3: typeの意図として正しいのはどれ

Multiple Choice
**Explanation:** RFC 7807 Section 3.1は`type`をproblem categoryを識別するURI referenceと定義します.documentationへdereferenceできるURIは一般的ですが必須ではありません.`type`を省略した場合は`about:blank`とみなされ,HTTP status codeがproblemの意味を与えます. A: statusがHTTP status B: typeの意味ではない C: errorの安定分類に使える

Q4: RFC 7807では, status memberを含める場合に何を入れるか

Multiple Choice
**Explanation:** RFC 7807 Section 3.1は,optionalな`status` memberを,この発生事象についてorigin serverが生成したHTTP status codeと定義します. intermediaryが転送中にresponse statusを変更する場合があるため, 汎用clientはpayloadを別系統のstatus authorityとせず, 実際のHTTP response statusを使います. A: client向けの便宜として, origin responseのstatusをpayloadにも示します. B: 標準memberのstatusは文字列ではなく数値です. C: statusは今回の発生事象を記述するもので, 後のresponseを予測しません.

Q5: problemの短いhuman readable summaryを表すmemberは何 (1語)

Short Text
**Explanation:** RFC 7807 Section 3.1は`title`をproblem typeの短いhuman-readable summaryと定義します.localizationを除けば,発生事象ごとに変えるものではありません.対して`detail`はこの発生事象を説明するため,requestごとに内容が変わり得ます.

Q6: 2つのエンドポイントがProblem Detailsの共通メンバーを返しつつ, それぞれ異なる拡張メンバーを定義している. 汎用クライアントが安全に仮定できることはどれ

Multiple Choice
**Explanation:** RFC 7807 Sections 3.1と3.2は,共通の標準memberとproblem type固有のextensionを分けます.extensionで標準memberの意味を上書きすることはできません. 汎用クライアントは標準メンバーを共通に処理できますが, 拡張を理解するには該当するproblem typeの定義が必要です. クライアントが拡張に依存する場合は, 人が読むためのdetailを解析せず, problem typeを確認して処理を分けます. A: 拡張はproblem type固有の情報を追加するものであり, エンドポイントごとに標準メンバーを再定義するものではありません. B: 標準メンバーは共通に扱え, 拡張はproblem type固有の情報を表します. C: RFC 7807は, 認識できない拡張メンバーを無視するようクライアントに求めており, problem typeを拡張可能にしています.
