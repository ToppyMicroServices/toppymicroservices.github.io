参照仕様

  • RFC 8615: Well-Known URIs

Q1: RFC 8615に対応するschemeで、well-known URIとなるpathはどれ？

単一選択
**解説:** A: path階層の最上位にある/.well-known/ prefixで始まる。 B: pathの途中に置かれた.well-knownは、定義上well-known URIではない。 C: RFC 8615はprefix自体のresource形式を定義せず、clientはその存在を期待すべきでない。

Q2: 新しいprotocolがsuffix "metadata/agents"を登録したい。問題はどれ？

単一選択
**解説:** A: registryへ登録するのは/.well-known/からのrelative suffixであり、先頭のslashは含めない。 B: registered nameは、slashを含まないsegment-nzに適合する必要がある。 C: RFC 8615はfile extensionを要求しない。

Q3: well-known URIの登録が最低限参照すべき定義はどれ？

単一選択
**解説:** A: RFC 8615はhostnameを選ばず、専用CAも定義しない。 B: redirectの動作はapplication固有であり、最低限必要な登録項目ではない。 C: 登録は、取得するrepresentationのformat・media typeと利用可能なschemeを定めるspecificationを参照する。

Q4: RFC 8615は、agent metadataを置くhostnameの選び方まで定める？

単一選択
**解説:** A: RFC 8615はissuerの概念やhostname選択規則を定義しない。 B: hostnameの決め方はapplicationへ委ねられている。 C: exampleのhostnameは例示であり、deployment要件ではない。

Q5: well-known URIからdocumentを取得しただけで、何を確認できる？

単一選択
**解説:** A: pathの規約だけでは、document内のclaimまでauthenticateしない。 B: metadataを信頼するには、pathへの配置とは別にapplicationが定めた検証が必要である。 C: RFC 8615はlocationの規約であり、operationをauthorizeする意味は持たない。

Q6: well-known metadataをHTTPSのdefault以外のportで提供する。何が必要？

単一選択
**解説:** A: suffixは代替portをencodeしない。 B: RFC 8615はport scanningをdiscovery手段として定義しない。 C: default以外のportを使う場合、applicationが明示しなければならない。

Q7: well-known locationへのwrite accessを厳しく制御すべき理由はどれ？

単一選択
**解説:** A: RFC 8615は一般にcacheを禁止しない。 B: 同居tenantがwrite accessを持つと、origin全体のdiscoveryへ影響できる。 C: media typeと処理modelはapplicationが定義する。

Q8: 無関係なWeb contentとHTTPS originを共有する場合、危険な前提はどれ？

単一選択
**解説:** A: 同じoriginの他contentもbrowser security mechanismを共有し、requestを発行しうる。 B: RFC 8615はsensitive dataの露出をdeployment上の懸念に挙げる。 C: identifier名に柔軟性を持たせると、origin内の衝突を減らせる。

Q9: 機密性の要件に対する設計レビューとして、最も適切なのはどれ？

単一選択

あるoriginは/.well-known/agent-cardでAgent Cardを公開している。Cardには公開endpointと、再利用可能なbootstrap用bearer tokenが含まれる。同じorigin上の無関係なWeb applicationはbrowser scriptを実行できるが、tokenは機密でなければならない。

**解説:** RFC 8615 Section 4.2は、well-known resourceもbrowserからaccessでき、同一originの他contentと相互作用することを警告している。このprefixは機密領域を作らない。Cは公開発見とtoken機密性の両方を満たす。Aは場所を隠すだけ、BはRFCにない隔離を仮定し、DはcredentialをURLに露出させる。

Q10: clientは発見したpolicyを二つのhostへ適用してよい？

単一選択

userがbilling.exampleを選び、clientはbilling.example/.well-known/a2aからHTTPS documentを取得した。documentはscopeを*.exampleと宣言し、admin.exampleをendpointとして示す。certificateとdocument signatureは有効だが、A2A profileにはhostname選択やoriginをまたぐscopeの規則がない。

**解説:** RFC 8615 Section 3は、hostnameの決定とmetadataのscopeをapplicationに委ねる。Section 4.3は、あるoriginのmetadataを別hostへ適用すると、実在しない管理関係を仮定する危険があると警告する。HTTPSとdocument signatureはchannelとsignerをそれぞれ認証しても、欠けているA2Aのauthority規則は補わない。Cが必要なprofile設計を示す。Dは強すぎる断定であり、RFCは別endpointへの参照を一律禁止していない。
