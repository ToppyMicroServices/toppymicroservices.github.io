Q1: TLS extensionの主な目的として最も近いのはどれ

Multiple Choice
**Explanation:** **TLS extension** は, protocol version を増やさずに追加 capability を交渉する仕組みです. 古い実装が理解できない extension は無視できるように設計されることが重要です. optional capabilityをextensionとして交渉できるため,protocol version全体を置き換えずに機能を追加できます. 拡張が増えるほど attack surface も増えます. だから negotiation の失敗時挙動や security considerations もセットで設計する必要があります. A: certificate関連のextensionはありますが, validationをapplication protocolへ移すframeworkではありません. B: backward compatibility を保ちながら機能追加する, という本質を表しています. C: optional extensionは, 全peerが新capabilityをsupportしなくても共存できるよう設計されます.

Q2: OCSP responseなどのcertificate status情報をhandshake中に送るようserverへ要求できるRFC 6066 extensionはどれ

Multiple Choice
**Explanation:** `status_request` extensionは, server certificateのstatus情報をTLS handshake内で配送するために使います. RFC 6066は対応する`CertificateStatus` handshake messageとOCSP response形式を定義しています. A: `trusted_ca_keys`はclientが保持するCA root keyを示します. B: `status_request`がcertificate status情報を要求するextensionです. C: `client_certificate_url`はclient certificate chainを直接送る代わりにURLを提示するために使います.

Q3: RFC 6066のserver_name HostName encoding ruleに従う値はどれ

Multiple Choice
**Explanation:** RFC 6066 Section 3は`HostName`を, clientが理解するfully qualified DNS hostnameのASCII byte stringとして定義し, trailing dotを認めません. internationalized nameはA-labelを使い, literal IPv4とIPv6 addressはこのfieldに入れられません. ここで問うのは表現ruleの適用なのでL2であり, 設計上のtrade-offは提示されていません. A: literal IP addressは`HostName`から明示的に除外されています. B: DNS nameとencodingの両constraintを満たします. C: raw UTF-8でもtrailing dot付きでもありません.

Q4: extension negotiationがうまく設計されているときの性質はどれ (複数選択)

Multi-Select
**Explanation:** **unknown extension を無視できる** ことは backward compatibility に重要で, **required / optional の明確化** は failure 時の挙動を決め, **security considerations** は attack surface を明文化します. unknown extensionの処理,required/optionalの境界,security considerationsを揃えることで,新機能を追加しても古い実装との相互運用とfailure時の判断を保てます. extension 設計では, feature そのものより failure mode の定義が interoperability を左右します. A: 未知の extension をどう扱うかは interoperability の土台です. B: required / optional が曖昧だと negotiation failure の意味が不明になります. C: extension は attack surface を増やすので, security considerations が欠かせません. D: 「全extensionは安全」と仮定するのは危険です. 拡張は新しいリスクも持ち込みます.

Q5: 1つのIPアドレスで2つのホスト名を提供し, ホスト名ごとに異なる証明書を使うTLSサーバがある. HTTPリクエストを受け取る前に証明書を選ぶため, ClientHelloのどの情報を使えるか

Multiple Choice
**Explanation:** SNIは, サーバが証明書を送る前に, ClientHelloの **server_name** 拡張でクライアントが要求するDNSホスト名を伝えます. RFC 6066では, サーバがserver_nameの情報を, クライアントへ返す適切な証明書の選択に利用できます. この仕組みにより, 1つのIPアドレスからホスト名ごとに異なる証明書を返す, 名前ベースのHTTPS仮想ホスティングが可能になります. A: ALPNはHTTP/2などのアプリケーションプロトコルを識別します. 要求されたホスト名を示す情報ではありません. B: SNIのserver_nameなら, 証明書を選ぶ時点で仮想ホストを区別できます. C: session ticketはセッション再開用の状態を運びます. 新しい仮想ホスト接続でホスト名を選ぶ情報ではありません.

Q6: TLS plaintext fragmentの最大長を小さくnegotiationするRFC 6066 extensionは何 (token 1つ)

Short Text
**Explanation:** `max_fragment_length`では,constrained clientがRFC 6066の定義するfragment sizeの1つをofferできます.serverは同じrequested valueをechoしてacceptし,異なる値や許可されない値はspecified ruleに従って`illegal_parameter` failureになります.
