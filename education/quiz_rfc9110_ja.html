Q1: 次のうち, HTTPのtransport詳細ではなくHTTPのセマンティクス(意味/ルール)に当たる話題はどれ

Multiple Choice
**Explanation:** **判断のポイント:** HTTP semanticsはprotocol version間で共通ですが, framingとtransport mechanismは変わります. **実務での機会:** API設計, proxy動作, client library, cache reviewではwire formatでなくmethodとresponseの意味を扱います. **Terms:** semantics(セマンティクス), transport, methodの意味. ここでのセマンティクスは, HTTP/1.1, HTTP/2, HTTP/3のどの運び方でも共通に成り立つ"意味/ルール"の話. **Protocol boundary:** HTTP/1.1のtext line, HTTP/2のframe, HTTP/3のQUIC streamではwire表現が異なりますが, GETのsafeやidempotentといったmethod semanticsは共通です. **Correct (A):** safe, idempotent, cacheable, status codeの意味はセマンティクスの中心です. これは transport が変わっても変わらない, HTTP そのものの意味づけです. **Options:** - A (correct): methodの意味と許される副作用の話. - B (incorrect): framingはtransport mappingの話. - C (incorrect): QUICのpacket挙動はtransportの話. **Related:** セマンティクスが分離されているから, プロキシやキャッシュは下位 transport と独立に判断できます. RFC 9110, 9112, 9113, 9114 を役割ごとに読むと全体像がつながります.

Q2: safeと定義されるmethodはどれ

Multiple Choice
**Explanation:** **判断のポイント:** safeは"serverが一切writeしない"という実装条件ではなく, clientが要求するactionの性質です. **実務での機会:** crawler, prefetch, link checker, cache最適化では, user確認なしに自動実行してよいmethodかを判断します. **Terms:** safe method. safeはdefined semanticsが本質的にread-onlyで, clientがstate changeを要求・期待しないことです. loggingなどclientが要求していない付随効果はあり得ます. **Correct (A):** GETは取得を要求するsafe methodです. implementation内部で付随効果が起き得ることとは両立します. **Options:** - A (correct): GETのdefined semanticsはsafeです. - B (incorrect): POSTは一般に状態変化を伴いsafeではない. - C (incorrect): DELETEは削除でありsafeではない. **Related:** safeはclientが要求するsemanticsの性質で, server内部に一切writeがないという保証ではありません. cacheableとも別概念です.

Q3: idempotentなmethodはどれ (複数選択)

Multi-Select
**Explanation:** **判断のポイント:** idempotencyは同一responseや, 全retryが運用上無条件に安全という保証と混同されやすい概念です. **Terms:** idempotent method. 同じリクエストを複数回送っても, 意図する効果が1回と同じになる性質. **Correct (A,C):** PUTとDELETEはidempotentとして定義されます. 同じrequestを繰り返したときのintended effectが1回と同じという意味で, 各responseや付随効果まで同じとは限りません. **Options:** - A (correct): PUTは置き換えなので繰り返しても収束する. - B (incorrect): POSTは通常idempotentではなく, 繰り返すと重複作成や二重処理になり得る. - C (correct): DELETEは最終的に"無い"状態へ収束する. - D (incorrect): CONNECTはトンネル確立で, 一般にidempotent扱いではない. **Related:** idempotencyはretry, LB, ネットワーク障害時の復旧設計で重要.

Q4: 3xxのstatus codeが一般に示すものはどれ

Multiple Choice
**Explanation:** **判断のポイント:** status-code classは, clientがcode固有の処理を行う前に読むresponse meaningの第一層です. **実務での機会:** client, gateway, monitoring, retry logicは, 個別codeを見る前にstatus classで大きな処理経路を選びます. **Terms:** status code class. 先頭の数字は仕様上の大分類を示す. **Correct (B):** 3xxはredirectionで, クライアントが追加の動作や別URIの使用を求められる. **Options:** - A (incorrect): 4xxがclient error. - B (correct): 3xxがredirection. - C (incorrect): 5xxがserver error. **Related:** 304 Not Modifiedも3xxで, cache validationの文脈で使われる.

Q5: If-Matchなどのrequest preconditionは, serverがいつ評価すべきか

Multiple Choice
**Explanation:** **判断のポイント:** conditional requestはcache validationだけでなくlost update防止にも使います. 評価時点を誤ると, errorの優先順を変えたりguard確認前にactionを実行したりします. **実務での機会:** document編集, 設定変更API, admin画面で, If-Matchを使って新しいstateの上書き事故を防ぎます. **用語:** **request precondition**は, **If-Match**などで現在のselected representationを条件にmethod実行をguardする仕組みです. **normal request check**は, significant processing前にrejectやredirectを決められる確認です. **Correct (C):** RFC 9110は, 除外条件を除き, normal request check成功後かつrequest content処理またはmethod actionの直前にpreconditionを評価するよう定めています. **Options:** - A (incorrect): significant processing前に分かるredirectやfailureが優先されます. unconditional responseが2xxでも412でもない場合, serverはpreconditionを無視します. - B (incorrect): action後ではlost updateなどのstate changeを防ぐには遅すぎます. - C (correct): normal error precedenceを保ちつつaction前にconditionを適用できます. **Related:** conditional fieldが複数ある場合の評価順はRFC 9110 Section 13.2.2が定めます. no-storeなどCache-Control directiveはRFC 9111の範囲です.

Q6: representationのmedia typeを示すheader fieldはどれ

Short Text
**Explanation:** **判断のポイント:** representation metadata fieldは名前が近くても役割が違い, 選択を誤るとrecipientがbyte列を誤解釈します. **実務での機会:** API client, browser, upload handler, security filterは, parserとdecode処理を選ぶときContent-Typeを使います. **Terms:** representation, media type. media typeはpayloadの解釈方法を受信側に伝える. **Correct:** Content-Type. **Why others are wrong:** Content-Lengthはサイズ, Acceptは希望, Hostはauthority. payloadの型を宣言しない. **Related:** charsetなどのparameterはデコードや安全性に影響する.
