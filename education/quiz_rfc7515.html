Q1: What does a valid JWS cryptographically protect?

Multiple Choice
**Explanation:** Only the JWS signing input is covered, not arbitrary enclosing data. The signature or MAC is computed over the protected-header and payload representation. Cryptographic integrity does not decide whether application claims are acceptable.

Q2: Where must a security-relevant JOSE header parameter be placed when its integrity matters?

Multiple Choice
**Explanation:** Protected-header bytes are included in the signing input. Unprotected header parameters are not integrity protected. An outer object is not covered unless the application explicitly includes it in the signed payload.

Q3: What is the role of the JWS "kid" header parameter?

Multiple Choice
**Explanation:** A key identifier does not establish ownership or trust. Algorithm policy and key identification are separate decisions. RFC 7515 defines kid as a hint and leaves its structure unspecified.

Q4: A JWS uses an algorithm that verifies mathematically but is disabled by local policy. Should it be accepted?

Multiple Choice
**Explanation:** RFC 7515 requires the algorithm to be acceptable to the application. A JWS is valid only after both cryptographic validation and application acceptance checks. A key hint cannot authorize a disallowed algorithm.

Q5: A protected header contains an extension listed in "crit" that the verifier does not understand. What should happen?

Multiple Choice
**Explanation:** Every parameter named by crit must be understood and processed. Ignoring an unknown critical parameter defeats the purpose of crit. A verifier cannot rewrite the sender's protected header without invalidating the signing input.

Q6: Which statement distinguishes Compact Serialization from JSON Serialization?

Multiple Choice
**Explanation:** Compact Serialization has no JWS Unprotected Header. Multiple signatures are provided by the general JSON serialization. These are capabilities of the JWS JSON serialization rather than the compact form.

Q7: A general JWS JSON object contains three signatures and the application requires two specific signers. What validation rule applies?

Multiple Choice
**Explanation:** RFC 7515 requires at least one but permits applications to require particular or multiple signatures. The application decides which signature values must validate and can require more than the base minimum. Array position does not define the application's signer policy.

Q8: A verifier fetches a JWK Set from a "jku" URL. Which check is still required?

Multiple Choice
**Explanation:** RFC 7515 requires integrity-protected retrieval and validated TLS server identity. Matching a hint does not establish a trusted key source. An attacker-controlled key source could provide a matching key and signature.

Q9: What does successful JWS validation not establish by itself for an Agent Card?

Multiple Choice
**Explanation:** This is the core cryptographic result of successful validation. Protected-header content participates in the signing input. Authority, issuer binding, audience, and freshness require application-profile rules.

Q10: Which review conclusion follows from RFC 7515?

Multiple Choice

An Agent Card wrapper contains a valid JWS plus unsigned `target` and `valid-until` members. The signed payload identifies the agent, but the gateway routes and authorizes requests using the two outer members. Its expected key and algorithm validate successfully.

**Explanation:** RFC 7515 Section 5.2 validates a signature over the JWS Signing Input: the encoded protected header and payload. JSON members merely adjacent to the JWS are outside that input. Moving or copying them after validation cannot change which bytes the signer covered. The application profile must decide which fields carry routing and authorization meaning, place them in integrity-protected content before signing, and define acceptable algorithms and trusted keys. Section 5.2 also makes algorithm acceptability an application decision even after the cryptographic operation succeeds. JWS validation does not by itself define claim semantics or freshness. RFC 7515 Section 10.10 describes replay protection as an application concern, for example by signing a unique message identifier and checking prior use. A valid signature is therefore necessary for the signed assertion, but not sufficient for this wrapper's acceptance decision.
