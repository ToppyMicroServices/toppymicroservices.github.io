Q1: Does RFC 8949 make CBOR data model sufficient for A2A authorization?

Multiple Choice

An A2A profile cites RFC 8949 and claims that using CBOR data model automatically settles peer acceptance and authorization.

**Explanation:** A: Sections 2-5 defines the mechanism, not all relying-party policy; the conclusion overclaims its effect. B: Sections 2-5 supports the mechanism statement, while the application still owns the stated policy boundary. C: A relationship to another specification does not transfer that specification's guarantees or local policy automatically. D: RFC 8949 still defines interoperable behavior within its scope; calling it guidance does not make processing arbitrary.

Q5: Which review response is justified when CBOR data model is used at an A2A trust boundary?

Multiple Choice

Intended use: when a binary protocol or token profile needs compact, typed, and extensible data. Observed defect: letting different encodings of the same abstract value break signatures, hashes, or cache keys.

**Explanation:** A: A mechanism's purpose does not establish that this instance or context is acceptable. B: Correct construction is necessary but not sufficient for verification and local acceptance. C: An adjacent specification cannot convert a failed or context-confused result into success. D: Section 10 supports resolving the defect before relying on the result. The profile rule is: choose deterministic encoding when bytes are compared, signed, or hashed across implementations. The check is: parse only well-formed CBOR and apply the application profile for duplicate keys, tags, and resource limits. The local policy is: the schema or profile that assigns meaning to map keys, tags, and allowed value types.
