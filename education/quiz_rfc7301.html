Q1: What problem does ALPN primarily solve

Multiple Choice
**Explanation:** **Why it matters:** ALPN is not specific to HTTP/2. It negotiates among multiple application protocols that can use the same secured endpoint. **Terms:** **ALPN** stands for **Application-Layer Protocol Negotiation**. It allows protocol selection to happen inside the TLS handshake instead of after the connection is already established. **Real-world usage:** In practice this matters on port 443 where a server may support HTTP/1.1, HTTP/2, or other protocols and wants to choose quickly without another round trip. **Options:** - A (incorrect): Advertising the target hostname is SNI's role; ALPN negotiates the application protocol. - B (correct): This is the central design goal of RFC 7301. - C (incorrect): ALPN completes protocol selection within the TLS hello exchange instead of adding a post-handshake negotiation. **Related:** The RFC was motivated in part by HTTP/2 over TLS, but the mechanism is general and can negotiate arbitrary application-layer protocols.

Q2: In a normal ALPN exchange, what does the client send

Multiple Choice
**Explanation:** **Why it matters:** The client proposes an ordered list, while the server makes the final selection from protocols it supports. **Terms:** In **ALPN**, the client advertises supported protocol identifiers in the **ClientHello**. The server selects one supported protocol from that list. **Real-world usage:** This matters when debugging a client that thinks it offered HTTP/2 but the server still negotiated HTTP/1.1 or failed the connection. **Options:** - A (correct): The client advertises candidates rather than making the final decision. - B (incorrect): The client does not force the server to accept exactly one pre-chosen protocol. - C (incorrect): Certificate chains are not carried as ALPN candidates. **Related:** Server-side preference still matters. The server usually chooses the most preferred protocol that both sides support.

Q3: Which statement best distinguishes ALPN from SNI

Multiple Choice
**Explanation:** **Why it matters:** ALPN and SNI can appear in the same handshake, but hostname routing and application-protocol negotiation are distinct decisions. **Terms:** **SNI** identifies the target server name. **ALPN** identifies the application protocol to use within the TLS-protected connection. **Real-world usage:** This distinction matters in load balancers, TLS terminators, and certificate debugging where the hostname and protocol choice influence different parts of the stack. **Options:** - A (incorrect): The responsibilities are reversed: SNI carries the server name, while ALPN negotiates the application protocol. - B (incorrect): SNI does not carry an application-protocol preference list; it identifies the target server name. - C (correct): It separates name-based virtual hosting from application-protocol selection on the TLS connection. **Related:** A server can use both pieces of information together, for example to route traffic and choose a certificate or protocol-specific backend behavior.

Q4: If the server supports none of the ALPN protocols advertised by the client, what should happen according to RFC 7301

Multiple Choice
**Explanation:** **Why it matters:** A failed protocol intersection becomes an explicit handshake failure instead of a completed TLS connection followed by an application mismatch. **Terms:** **no_application_protocol** is the alert used when there is no common application protocol between client and server. **Real-world usage:** This shows up when clients offer only `h2`, servers support only HTTP/1.1 over TLS, or proxies strip or mis-handle ALPN configuration. **Options:** - A (incorrect): The server must not invent a protocol the client did not advertise. - B (correct): This is the RFC-defined failure behavior. - C (incorrect): Downgrading to plaintext is not an ALPN fallback. **Related:** Clean failure is important because “pick something else and hope” produces hard-to-debug protocol mismatches and false confidence.

Q5: Why does RFC 7301 mention certificate selection as a design benefit of ALPN

Multiple Choice
**Explanation:** **Why it matters:** ALPN can influence deployment decisions such as certificate selection and backend routing, not only protocol compatibility. **Terms:** **certificate selection** means the server may choose among possible certificates based on the negotiated application protocol. **routing behavior** can also differ by negotiated protocol. **Real-world usage:** This matters in multi-tenant ingress, TLS offload layers, and environments where protocol choice influences which backend or credential chain is appropriate. **Options:** - A (correct): This captures the design motivation described by the RFC. - B (incorrect): Clients do not upload replacement certificates through ALPN. - C (incorrect): Certificate validation remains essential. **Related:** Protocol negotiation, hostname indication, and certificate selection are distinct concerns, but real deployments often make them interact.

Q6: Which statements about ALPN visibility are generally true (select all)

Multi-Select
**Explanation:** **Why it matters:** The advertised and selected application protocols can expose metadata even though ALPN is a negotiation mechanism. **Terms:** An **externally visible marker** is something on-path systems may infer before application data is exchanged. ALPN protocol identifiers can become such markers depending on TLS version and deployment. **Real-world usage:** This matters when protocol identifiers themselves are sensitive, when profiling risk exists, or when network elements make differentiated-service decisions based on protocol choice. **Options:** - A (correct): The RFC warns that in earlier TLS versions the client's protocol identifiers can be visible. - B (incorrect): ALPN was not designed to hide protocol choice pre-connection. - C (correct): This is explicitly part of the RFC's design discussion. - D (incorrect): The RFC does not provide such a guarantee and instead warns about leakage risk. **Related:** If protocol secrecy matters, you need a design that truly hides the selection rather than assuming the ALPN field does that automatically.

Q7: What does it mean that the protocol selected by ALPN is definitive for the connection

Multiple Choice
**Explanation:** **Why it matters:** The server's selected protocol is the definitive protocol for that connection, not an advisory hint. **Terms:** **definitive for the connection** means the selected application protocol is the one that governs application data exchange on that TLS connection. **Real-world usage:** This matters in reverse proxies and TLS terminators. If the front end reports `h2` but the backend logic speaks something else, failures become subtle and severe. **Options:** - A (incorrect): A second implicit selection would reintroduce the ambiguity that ALPN resolves in the TLS handshake. - B (incorrect): ALPN selects the application protocol for the connection; it is not merely a TLS record-layer label. - C (correct): The ServerHello result determines what both endpoints are expected to speak on that connection. **Related:** Protocol negotiation is useful precisely because it reduces ambiguity about what both sides should speak after the handshake completes.

Q8: During session resumption, how should ALPN be treated according to RFC 7301

Multiple Choice
**Explanation:** **Why it matters:** ALPN is a connection property. Resumption does not let the previous session's protocol selection replace negotiation in the current handshake. **Terms:** A **connection property** applies to the current handshake and connection instance. ALPN is negotiated per connection, even when resumption is used. **Real-world usage:** This matters when a client resumes to the same endpoint but offers different protocol support or when server configuration has changed since the earlier connection. **Options:** - A (correct): The new handshake controls the current connection's ALPN outcome. - B (incorrect): ALPN is not pinned to the prior session in that way. - C (incorrect): There is no plaintext side negotiation replacing ALPN here. **Related:** This distinction is important because confusing session properties with connection properties leads to stale assumptions in TLS debugging.

Q9: A ClientHello offers `h2` and `http/1.1`. TLS completes, but the client reports that no ALPN value was negotiated. Which explanation is consistent

Multiple Choice
**Explanation:** **Why it matters:** A completed TLS handshake does not by itself prove that ALPN was negotiated. A peer that does not support or process the extension can complete TLS without returning an ALPN selection. **Terms:** A server that returns the ALPN extension selects exactly one protocol from the client's advertised list. A server that does not process the extension returns no ALPN selection. **Real-world usage:** Diagnostic tools need to distinguish no ALPN selection from an explicit `http/1.1` selection because the two states can lead to similar application-level observations. **Options:** - A (incorrect): SNI carries the intended server name. It neither selects `h2` nor suppresses an ALPN result. - B (correct): TLS extension compatibility permits a server that does not process ALPN to omit the response extension. - C (incorrect): A server that returns ALPN must select exactly one protocol from the client's advertised list. **Related:** Check the negotiated ALPN field directly instead of inferring it from the ClientHello offer or the resulting HTTP behavior.

Q10: A ClientHello advertises ALPN protocols `h2`, then `http/1.1`. The server supports both and prefers `http/1.1`, then `h2`. Which selection follows RFC 7301

Multiple Choice
**Explanation:** RFC 7301 Section 3.2 expects a server to maintain its own preference order. It should select its highest-preference protocol that it supports and that the client advertised. **Options:** - A (incorrect): The client list communicates support and client preference, but RFC 7301 assigns the final selection to the server. - B (correct): Both protocols are common, and `http/1.1` is first in the server's preference order. - C (incorrect): The fatal alert applies when there is no common advertised protocol, not merely when the preference orders differ. **Related:** Once selected, the ServerHello ALPN value is definitive for the connection; the server must not later exchange application data using a different protocol.
