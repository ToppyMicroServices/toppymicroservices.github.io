Q1: 仕様に "Clients must validate certificates" とあり, BCP 14の解釈が明示されていない. 起きやすい問題はどれ

Multiple Choice
**Explanation:** must (小文字), 規範要件, BCP 14, 曖昧性. 要件は, 実装者が同じ解釈で適合判定できることが重要. 規範語が **ALL CAPS** で書かれ, 文書がBCP 14の解釈を宣言していれば, 特別なキーワードの意味を一意に適用できます. どちらかが曖昧だと, mustの重さが読み手によって変わります. BCP 14の解釈が宣言されていないと, mustを厳密な要件として読む人と, 強い言い回しとして読む人が混ざり, 実装が割れやすい. RFC 8174 は, まさにこの曖昧性を減らすための文書です. セキュリティ要件は, テスト可能な条件として書き, 規範語の解釈を明示する. だから RFC 2119 と RFC 8174 は, 仕様を書く人だけでなく読む人にも効く RFC です. A: 小文字mustを必ず規範語として読む根拠は, 文書が明示しない限り成立しない. B: これが最も起きやすい問題. 同じ仕様を読んでも結論が分岐する. C: 文は意味を持つ. 問題は有効性ではなく, 規範性の明確さ.

Q2: 要件にBCP 14のMUSTとしての特別な意味を持たせたい. 最も明確な書き方はどれ

Multiple Choice
**Explanation:** MUST, 規範語, BCP 14ボイラープレート, 大文字小文字. RFC 8174のボイラープレートは, 列挙した語がすべて大文字で現れる場合に限り, BCP 14の定義どおりに解釈すると宣言します. 宣言と大文字のキーワードを揃えることで, 意図が明確になります. 文書が別の規則を明示的に定義することはできますが, RFC 8174の標準ボイラープレートが小文字にもBCP 14の意味を与えるとは説明できません. A: すべて大文字のMUSTが大文字条件を満たし, ボイラープレートがBCP 14の解釈を宣言します. B: RFC 8174の標準ボイラープレートでは, 小文字のmustにBCP 14の特別な意味は与えられません. C: 例は動作を説明できますが, 必須の適合条件を宣言する代わりにはなりません.

Q3: 実装者の曖昧性を減らす実践はどれ (複数選択)

Multi-Select
**Explanation:** 曖昧性, BCP 14キーワード, MUST, SHOULD. RFC 8174の狙いは, キーワードの読み方を明示して, 要件を一意に読むこと. レビューでは, "このMUSTはどう試験する" と "このSHOULDの例外は何" を確認する. A: MUST/SHOULD/MAYの意味の前提を固定できる. B: 何が要件で何が説明かが不明になり, 実装差が増える. C: MUSTがテスト可能なら, 実装とレビューが収束しやすい. D: SHOULDは例外を許す. 例外が曖昧だと, SHOULDが実質MAYになる.

Q4: 仕様の冒頭に, 「BCP 14キーワードはすべて大文字の場合に限り, 定義された意味を持つ」とある. 後の本文に "clients should retry" と書かれている. 小文字のshouldをどう解釈するか

Multiple Choice
**Explanation:** **SHOULD** はBCP 14キーワードです. RFC 8174の「すべて大文字」という規則を採用した文書では, 小文字の **should** は通常の英語の意味を持ちます. RFC 8174が定義するBCP 14の特別な意味は, すべて大文字の表記だけに与えられます. 文書が別の規則を定義することはできますが, この定型文だけでは小文字の **should** は規範的 **SHOULD** になりません. BCP 14キーワードを使わない規範文も書けますが, その要件は小文字の綴りから推測させず, 本文で明確にする必要があります. A: すべて大文字という条件があるため, 大文字小文字は解釈に影響します. あらゆる表記を規範語にする宣言ではありません. B: 文書が小文字に別の意味を明示しない限り, 通常の英語として読みます. C: 小文字にすると別のBCP 14キーワードへ変わるのではなく, この規則では特別なBCP 14の意味を失います.

Q5: 文書が標準のBCP 14ボイラープレートを採用している. testableな必須要件を最も明確に表す文はどれ

Multiple Choice
**Explanation:** BCP 14, 規範セクション, MUST. RFC 8174とRFC 2119の文脈では, MUSTのようなキーワードで適合要件を表現する. MUSTが動作をmandatoryと示し, 参照した構文がimplementation-independentでtestableなconditionを与えます. 正当な例外がある場合は, circularなescape clauseではなく, 理由と適用conditionを示してSHOULDを使います. A: 標準ボイラープレートでは通常の日本語に埋め込んだ「方がよい」にBCP 14の特別な意味はなく, normative forceが不明確です. B: すべて大文字のMUSTが宣言済みのBCP 14意味を持ち, 具体的なconditionへ適用されています. C: SHOULDは例外を許しますが, この文は例外を選ぶ実質的なconditionを示していません.

Q6: implementationがある動作を含めるか省くかを自由に選べると示すBCP 14キーワードは何 (1語)

Short Text
**Explanation:** optional behavior, 規範語, MAY. BCP 14では, itemがtruly optionalな場合にMAYを使います. MAYはimplementationがその動作を含めるか省くかを選べることを示します. 仕様に定めがあれば, 異なる選択をしたpeer同士でもinteroperateする必要があります. MUSTは絶対要件です. SHOULDは正当な例外を許す推奨です. どちらもfeature自体が自由選択という意味ではありません. optional featureでも, peerがその有無を検出し, 未対応時にどう動くかというinteroperability boundaryは定義します.
