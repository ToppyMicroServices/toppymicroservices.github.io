  • RFC 7617: The "Basic" HTTP Authentication Scheme

Q1: Basic認証のcredentialを送るrequest headerはどれ

Multiple Choice
**Explanation:** Basic challengeは`WWW-Authenticate`で運ばれ, clientのcredential responseは`Authorization` request headerを使います. clientは`Authorization: Basic <token68>`を送ります. `Authorization`はHTTP authentication frameworkがcredential用に定義するrequest fieldです. `Authenticate`というrequest fieldはなく, server challengeには`WWW-Authenticate`を使います. `Cookie`は別のstate mechanismであり, Basic credential fieldではありません. proxy authenticationでは`Authorization`ではなく`Proxy-Authorization`を使います.

Q2: Basic認証のcredentialは一般にどう符号化される

Multiple Choice
**Explanation:** Basicはuser-id, 1つのcolon, passwordを連結して`user-pass`を作り, character sequenceをoctetへ変換してからBase64で符号化します. Base64は表現を変えるだけで, confidentialityを提供しません. wire上のBasic tokenはpassword hashではなく, Base64から元のuser-pass octetを復元できます. Basicはserver public keyでcredentialを暗号化しません. character encodingの段階とBase64の段階を分けたconstructionです. default character encodingは一意に固定されておらず, challengeは`charset="UTF-8"`を提示できます.

Q3: TLSなしのBasic認証が危険な理由として正しいのはどれ

Multiple Choice
**Explanation:** Base64はreversibleなbinary-to-text encodingであり, decodeにsecret keyを必要としません. unprotectedなBasic credentialをpassive observerが取得すると, user-idとpasswordを復元できます. BasicはHTTP authentication semanticsで動き, HTTP/2と本質的に非互換ではありません. credentialをin transitで守るにはTLSなどのexternal secure channelが必要です. Basic自体がbrowser cookieをcross-siteへ送信させるわけではありません. passwordを使い回していると, 1つのBasic credential漏えいが別systemのaccountにも波及します.

Q4: Basic認証challengeでよく使うstatus codeはどれ

Multiple Choice
**Explanation:** RFC 7617 Section 2では, origin serverが401 responseと`WWW-Authenticate` fieldでBasic challengeを送り, clientが後続requestの`Authorization` fieldでcredentialを提示します. 206はpartial content, 302はredirectです. proxy authenticationはoriginの401とは別に407と`Proxy-Authenticate`を使います.

Q5: Basic認証credentialの運用上のbest practiceとして近いのはどれ

Multiple Choice
**Explanation:** Basic credentialは再利用可能なsecretなので, TLSで通信経路を保護するだけでなく, redirect, debug output, proxy logへの転送や記録も制限します. **Authorization header** は credential を直接含む sensitive data です. untrusted origin への転送や log 出力は, そのまま secret 漏えいになります. best practice に近いのは, **untrusted origin へ送らず, log にも残さない**ことです. URL に入れると browser history, log, analytics, referer などから漏れやすくなります. decode した値を log に出すのは最悪の運用です. trust boundary を越える前に header を落とし, storage にも残さないのが基本です. reverse proxy や redirect handler では, `Authorization` をどこで strip するかを明示しておくと事故が減ります.

Q6: serverがuser-passにUTF-8を期待すると提示するBasic challenge parameterは何 (1語)

Short Text
**Explanation:** optionalな**`charset`** authentication parameterはBasic challengeに現れます. RFC 7617で定義される値はcase-insensitiveな`UTF-8`だけです. このparameterはadvisoryであり, Base64より前にuser-pass characterをoctetへ変換する方法を扱います. encryption settingでもcredential token内のfieldでもありません. character encodingについて合意できないと, non-ASCIIのuser-idやpasswordでinteroperability failureが起きます.

Q7: RFC 7617が最も強く支持するcredential-handling decisionはどれか

Multiple Choice

agentが`https://api.example/tasks/7`へHTTPS上のBasicでauthenticateします. originは`https://collector.example/import`へredirectします. client libraryは同じ`Authorization` fieldを転送し, decoded valueをdebug logへ記録しようとしています.

**Explanation:** RFC 7617 Section 2.2がpreemptive reuseを認めるのはprotection spaceのauthentication scope内です. 同sectionの例ではscheme変更もscope外であり, 異なるauthorityもoriginal originのprotection spaceではありません. redirectはnew originへcredentialを渡すpermissionを作りません. Section 4はBasic passwordが容易にreverseできる形で送られ, sensitive informationの保護にHTTPSなしで使うべきでないと説明します. Base64の再encodeはfreshnessもconfidentialityも作りません. 値はreusable secretのままなので, decoded formのloggingは別のdisclosure pathになります. logへ残さない判断はこのthreatから導くdeployment上の対策であり, RFC 7617が別個のwire-format ruleとして規定するものではありません. new originは自身にapplicableなchallengeを出すか, applicationが明示的なcredential policyを適用できます. redirect handlingだけでfirst originのcredentialを取得させてはいけません.
