Q1: Basic認証のcredentialを送るrequest headerはどれ

Multiple Choice
**Explanation:** **Terms:** Basic challengeは`WWW-Authenticate`で運ばれ, clientのcredential responseは`Authorization` request headerを使います. **Correct (A):** clientは`Authorization: Basic `を送ります. **Options:** - A (correct): `Authorization`はHTTP authentication frameworkがcredential用に定義するrequest fieldです. - B (incorrect): `Authenticate`というrequest fieldはなく, server challengeには`WWW-Authenticate`を使います. - C (incorrect): `Cookie`は別のstate mechanismであり, Basic credential fieldではありません. **Related:** proxy authenticationでは`Authorization`ではなく`Proxy-Authorization`を使います.

Q2: Basic認証のcredentialは一般にどう符号化される

Multiple Choice
**Explanation:** **Terms:** Basicはuser-id, 1つのcolon, passwordを連結して`user-pass`を作り, character sequenceをoctetへ変換してからBase64で符号化します. **Correct (C):** Base64は表現を変えるだけで, confidentialityを提供しません. **Options:** - A (incorrect): wire上のBasic tokenはpassword hashではなく, Base64から元のuser-pass octetを復元できます. - B (incorrect): Basicはserver public keyでcredentialを暗号化しません. - C (correct): character encodingの段階とBase64の段階を分けたconstructionです. **Related:** default character encodingは一意に固定されておらず, challengeは`charset="UTF-8"`を提示できます.

Q3: TLSなしのBasic認証が危険な理由として正しいのはどれ

Multiple Choice
**Explanation:** **Terms:** Base64はreversibleなbinary-to-text encodingであり, decodeにsecret keyを必要としません. **Correct (B):** unprotectedなBasic credentialをpassive observerが取得すると, user-idとpasswordを復元できます. **Options:** - A (incorrect): BasicはHTTP authentication semanticsで動き, HTTP/2と本質的に非互換ではありません. - B (correct): credentialをin transitで守るにはTLSなどのexternal secure channelが必要です. - C (incorrect): Basic自体がbrowser cookieをcross-siteへ送信させるわけではありません. **Related:** passwordを使い回していると, 1つのBasic credential漏えいが別systemのaccountにも波及します.

Q4: Basic認証challengeでよく使うstatus codeはどれ

Multiple Choice
**Explanation:** **判断のポイント:** origin serverは401 responseの`WWW-Authenticate`でchallengeを送り, clientは後続requestの`Authorization`でcredentialを返します. **用語:** 認証 challenge では server が **401 Unauthorized** と **`WWW-Authenticate`** header を返し, client が次の request で **`Authorization`** header を送ります. **Correct (A):** Basic challenge でよく使う status code は **401** です. **選択肢:** - A (correct): challenge と `WWW-Authenticate` を伴う代表的な status code です. - B (incorrect): **206** は partial content の status code で, Basic challenge とは無関係です. - C (incorrect): **302** は redirect であり, 認証 challenge の中心ではありません. **関連:** 「401 + `WWW-Authenticate` -> 次 request で `Authorization`」という流れをセットで覚えると実装や debug が楽になります.

Q5: Basic認証credentialの運用上のbest practiceとして近いのはどれ

Multiple Choice
**Explanation:** **判断のポイント:** Basic credentialは再利用可能なsecretなので, TLSで通信経路を保護するだけでなく, redirect, debug output, proxy logへの転送や記録も制限します. **用語:** **Authorization header** は credential を直接含む sensitive data です. untrusted origin への転送や log 出力は, そのまま secret 漏えいになります. **Correct (C):** best practice に近いのは, **untrusted origin へ送らず, log にも残さない**ことです. **選択肢:** - A (incorrect): URL に入れると browser history, log, analytics, referer などから漏れやすくなります. - B (incorrect): decode した値を log に出すのは最悪の運用です. - C (correct): trust boundary を越える前に header を落とし, storage にも残さないのが基本です. **関連:** reverse proxy や redirect handler では, `Authorization` をどこで strip するかを明示しておくと事故が減ります.

Q6: serverがuser-passにUTF-8を期待すると提示するBasic challenge parameterは何 (1語)

Short Text
**Explanation:** **用語:** optionalな**`charset`** authentication parameterはBasic challengeに現れます. RFC 7617で定義される値はcase-insensitiveな`UTF-8`だけです. **Correct:** **charset**. **Why this matters:** このparameterはadvisoryであり, Base64より前にuser-pass characterをoctetへ変換する方法を扱います. encryption settingでもcredential token内のfieldでもありません. **Related:** character encodingについて合意できないと, non-ASCIIのuser-idやpasswordでinteroperability failureが起きます.
