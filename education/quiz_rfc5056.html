Q1: Does RFC 5056 make channel binding sufficient for A2A authorization?

Multiple Choice

An A2A profile cites RFC 5056 and claims that using channel binding automatically settles peer acceptance and authorization.

**Explanation:** A: Sections 2-3 defines the mechanism, not all relying-party policy; the conclusion overclaims its effect. B: Sections 2-3 supports the mechanism statement, while the application still owns the stated policy boundary. C: A relationship to another specification does not transfer that specification's guarantees or local policy automatically. D: RFC 5056 still defines interoperable behavior within its scope; calling it guidance does not make processing arbitrary.

Q2: Two implementations reach incompatible results for channel binding. What must the profile define?

**Explanation:** A: Acceptance policy cannot repair incompatible construction inputs or encodings. B: A nearby specification relationship does not define this profile's omitted construction rule. D: Two locally successful but unequal outputs are not interoperable merely because both implementations accept themselves.

Q5: Which review response is justified when channel binding is used at an A2A trust boundary?

Multiple Choice

Intended use: when a SASL, token, or application proof must be tied to the protected connection. Observed defect: treating hostname, token audience, or unauthenticated metadata as if it were channel binding data.

**Explanation:** A: A mechanism's purpose does not establish that this instance or context is acceptable.
