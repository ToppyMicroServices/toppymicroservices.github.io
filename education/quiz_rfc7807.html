Q1: What is the media type for a JSON Problem Details response

Multiple Choice
**Explanation:** RFC 7807 Section 6.1 registers `application/problem+json` so recipients can recognize both the JSON encoding and the Problem Details semantics. Plain `application/json` identifies only the serialization. Section 6.2 separately registers `application/problem+xml` for XML. A: It can work but does not convey the Problem Details semantics B: Standard for JSON problem details C: Not defined

Q2: Which are standard members of a Problem Details object (select all)

Multi-Select
**Explanation:** RFC 7807 Section 3.1 defines `type`, `title`, `status`, `detail`, and `instance`. Section 3.2 permits a problem type to add extension members, but `stackTrace` is not a standard member and would need an explicitly documented problem-type definition. Clients that do not recognize an extension must ignore it. A: type identifies the problem type with a URI reference. B: title is a short, human-readable summary of the problem type. C: status carries the HTTP status code generated by the origin server for this occurrence. D: detail gives a human-readable explanation specific to this occurrence. E: instance is a URI reference identifying this particular occurrence. F: stackTrace is not a standard member and can expose implementation details.

Q3: What is the intended meaning of type

Multiple Choice
**Explanation:** RFC 7807 Section 3.1 defines `type` as a URI reference that identifies the problem category. A dereferenceable documentation URI is common but not required. When `type` is absent, its value is assumed to be `about:blank`, which gives the problem the semantics of its HTTP status code. A: status is the HTTP status code B: host is not the meaning of type C: This enables stable categorization of errors

Q4: According to RFC 7807, what should the status member contain when it is present

Multiple Choice
**Explanation:** RFC 7807 Section 3.1 defines the optional `status` member as the HTTP status code generated by the origin server for this occurrence. An intermediary can change the response status in transit, so a generic client should use the actual HTTP response status rather than treat the payload member as a separate authority. A: It duplicates the origin response status as a convenience for clients. B: status is numeric in the standard members C: status describes this occurrence; it does not predict a later response.

Q5: Which member is a short human readable summary of the problem (one word)

Short Text
**Explanation:** RFC 7807 Section 3.1 defines `title` as the short, human-readable summary of a problem type. Except for localization, it should remain stable across occurrences. By contrast, `detail` describes this particular occurrence and can vary between requests.

Q6: Two endpoints return the common Problem Details base members but define different extension members. What may a generic client safely assume

Multiple Choice
**Explanation:** RFC 7807 Sections 3.1 and 3.2 separate common base members from problem-type-specific extensions. An extension cannot redefine the standard members. A generic client can process the standard members consistently, but it needs the problem type's definition to understand that type's extensions. A client should branch on the problem type before relying on an extension, rather than parsing the human-readable detail member. A: Extensions add problem-specific information; they do not redefine the standard members for each endpoint. B: The base vocabulary is shared while extensions carry type-specific semantics. C: RFC 7807 requires clients to ignore extension members they do not recognize, allowing problem types to evolve.
