Q1: このgateway設計をRFC 1958 Section 2.3でreviewするとき,最も適切な結論はどれか

Multiple Choice

A2Aのedge gatewayがgrantとsession-bound proofを検証し,保護されたidentity assertionだけをbackendへ転送します.resourceを所有するbackendは,元のgrantやproofを検証せず,そのassertionから最終authorizationを判断します.

**Explanation:** A: RFC 1958 Section 2.3は,network側の不完全な機能も補助として有用になり得ると説明しており,gatewayでの処理を一律に禁止していません.またRFC 1958はInformationalです. B: gateway-backend hopの保護は,採用するmechanismに応じてそのhopでの送信元と完全性を保証できますが,元のclient TLS sessionとのbindingを自動的には継承しません. C: Section 2.3のend-to-end argumentは,完全な機能の実現にapplication endpointの知識が必要かを問うreview lensです.gatewayをsecurity endpointとして信頼するなら,backendが受け取るassertionの意味,真正性,失効,再利用防止をそのtrust modelで定義します.元のsessionまでbackendが検証すべきなら,検証可能な証拠または別のbinding設計が必要です. D: grantの有効性はauthorizationの一条件であり,requestが意図したsecure channel instanceに結び付くかとは別の保証です.

Q2: RFC 1958 Sections 2.1-2.3を使ったreviewとして,最も適切な指摘はどれか

Multiple Choice

二つのA2A実装はIPでは到達できますが,特定事業者のgatewayがtask stateとauthorizationの意味を相互変換しない限り通信できません.endpointはgatewayなしでは同じ意味を復元できません.

**Explanation:** A: Sections 2.1-2.3はend-to-end intelligenceを重視しますが,特定の物理配置をnormativeに禁止する規定ではありません. B: IP reachabilityだけでは,A2A messageの意味と相互運用性がendpoint間で保たれるとは限りません. C: reviewすべき点は,不可欠なapplication semanticsを誰が所有し,gateway failureや事業者変更の後もendpointが相互運用できるかです.gatewayをendpointとするなら,その責務とtrustを明示します. D: vendor統一はdependencyを消さず,global connectivityやfailure isolationの保証にもなりません.

Q3: RFC 1958 Section 2.3に沿ったintegrity設計はどれか

Multiple Choice

agentが承認済みの2 GB artifactを送ります.gatewayはchunkへ分割し,object storeで再構成します.各hopはTLSとchunk checksumを使いますが,backendは承認されたartifact全体と同一であることを判断する必要があります.

**Explanation:** A: hop-level protectionが覆うのは各区間またはchunkであり,分割,保存,再構成を通じたobject全体の同一性までは保証しません. B: applicationが必要とする完全な機能は,承認時と受信時で同じcanonicalization boundaryを使うend-to-end proofで確認します.lower-layer checkはperformanceとrecoveryの補助として残せます. C: 到着順のlogはcontent integrityを証明せず,log自体の真正性や欠落も別問題です. D: storeの完了通知は処理状態であり,承認されたbytesまたは意味との一致を示しません.

Q4: RFC 1958 Section 2.3のfate-sharingとself-healing stateを反映する改善はどれか.複数選択

Multi-Select

stateful relayがtaskとstream subscriberの対応をmemoryだけに保持します.relayが再起動すると,agentとtask storeは正常でもtaskの再開先を復元できず,taskが永久に孤立します.

**Explanation:** A: endpointまたはlogical task ownerとstateの寿命を揃えれば,relayだけのfailureでauthoritative stateが失われません. B: replicationはavailabilityを改善し得ますが,同じfailure modeと再生成不能なstateを残したままではfate-sharingの代わりになりません. C: RFC 1958はnetwork-maintained stateをadaptive procedureで修復し,connectivityがある場合のlossをtemporary denial of service以下に抑える考えを示します. D: state量とcross-component dependencyを減らすことは,復旧範囲とfailure amplificationを小さくします. E: 無期限の全量保存はcostとcouplingを増やし,state最小化に反します.

Q5: RFC 1958 Sections 2.4 and 3.14に照らし,proposal Xの結果から言えることはどれか

Multiple Choice

A2A profile Xは二つの独立実装がloss,並べ替え,version mismatchを含む試験で相互運用しました.profile Yは詳細なformal modelを持ちますが,実装は一つだけです.どちらも大規模運用と攻撃耐性は未評価です.

**Explanation:** A: running codeは重要ですが,観測していないsecurity,scale,operationの性質まで証明しません. B: formal reasoningと実装feedbackは補完関係であり,一方が常に他方を無効にするわけではありません. C: Sections 2.4 and 3.14はreal implementationからのfeedbackを重視します.結論は実際に試した条件へ限定し,残るclaimには別のevidenceを要求します. D: 独立実装であることと試験条件は,相互運用性の証拠を評価する中心情報です.

Q6: RFC 1958 Sections 3.1,3.3,3.4に基づく次のreview actionはどれか

Multiple Choice

新しいA2A streaming profileは固定200 ms deadline,最低8 MB buffer,高頻度heartbeatを必須にします.datacenter試験は成功しましたが,mobile agentではtimeoutし,100万のidle agentではcontrol trafficが支配的になります.

**Explanation:** A: 一つの均質な環境を前提にすると,heterogeneityとdeployment可能性を設計から排除します. B: RFC 1958はheterogeneity,大規模scale,performance,costをfunctionalityと同時に評価するよう求めます.固定値がprotocol semanticsか調整可能なpolicyかも分けます. C: option化だけではcomplexityを解決せず,未定義の組合せとinteroperability failureを増やします. D: 将来のhardwareを仮定して現在のscale failureを無視することは,engineering evidenceになりません.

Q7: RFC 1958 Section 3.2を設計判断へ適用した結論はどれか

Multiple Choice

配備済みのAgent Card discoveryは必要なmetadata,caching,authenticationを扱えます.新proposalは同じ情報を別の非互換registryで表し,全実装に無期限のdual lookupを要求しますが,既存方式で解けないfailureは示していません.

**Explanation:** A: 重複機能は実装分岐と相互運用matrixを増やすため,option数自体は利点ではありません. B: Section 3.2は成功した解の再利用を勧めますが,good technical reasonがある改善を拒否する根拠にはしないと明記します. C: 既存解をdefaultとしつつ,新方式の測定可能なbenefitとmigration costを比較するのが原則を設計判断へ使う方法です. D: localなschemaの単純さだけでは,ecosystem全体のdual behaviorと移行failureを正当化できません.

Q8: RFC 1958 Sections 3.5-3.8を反映するprofile改訂はどれか.複数選択

Multi-Select

A2A profileにretry,compression,signing,streamingを制御する14個のmanual flagがあり,一部の組合せは結果が未定義です.operatorごとに設定が異なり,接続時に互いの選択を確認しません.

**Explanation:** A: Sections 3.5 and 3.8はsimpleな解を選び,不要なoptionとparameterを避ける方向を示します. B: manual choiceを増やすとconfiguration driftと未検証の組合せが増え,interoperabilityを弱めます. C: Section 3.6のmodularityは,分離できる責務の変更とfailureの影響範囲を閉じるために使えます. D: 必要なvariationはdynamic negotiationできますが,negotiation結果とfailure behaviorを仕様化する必要があります. E: Section 3.7はperfect solutionを無期限に待つことを避け,almost completeな解からfeedbackを得る余地を認めます.

Q9: RFC 1958 Section 3.11に基づくbootstrap reviewとして適切なのはどれか

Multiple Choice

Agent Cardの取得にはOAuth access tokenが必要です.clientがauthorization serverと利用可能な認証方式を知る唯一の方法は,そのAgent Cardを読むことです.clientには事前設定されたbootstrap情報がありません.

**Explanation:** A: fate-sharingは必要なstateのfailure boundaryを揃える考えで,相互に開始不能なdependencyを正当化しません. B: clientはtokenなしにCardを読めず,Cardなしにtoken取得先を知れません.publicでauthenticityを検証できるmetadata,独立したdiscovery,またはpreconfigurationなどでcycleを切ります. C: 情報が欠けたrequestのretryはbootstrap情報を生成せず,loadとdelayを増やすだけです. D: token強度はcredential guessingへ影響しますが,issuer discoveryの欠落とは独立です.

Q10: RFC 1958 Sections 6.3-6.5を現在のA2A署名profileへ適用したreview conclusionはどれか

Multiple Choice

profile v1はAlgorithm Aだけを固定し,署名対象にalgorithm identifierを含めません.Algorithm Bへの移行案は,integrity保護されないheaderでAまたはBを指定します.異なる実装間のsecure interoperabilityも必要です.

**Explanation:** A: permanent pinningはalgorithm replacementを困難にし,Section 6.3が求めるalternativeへの設計余地を失います. B: labelが攻撃者に書き換えられると,弱いalgorithmへのdowngradeやverification confusionを防げません.識別子をproofの保護範囲へ結び付けます. C: Section 6.5はsecure contextを相互運用できるよう,少なくとも一つの共通algorithmまたはsuiteを求めます. D: Sections 6.3-6.5のagility,labeling,strength,common suiteを満たしつつ,negotiation integrityとdowngradeを明示的に扱います.RFC 1958は特定algorithmの現在の安全性までは証明しないため,acceptanceは最新のevidenceとpolicyで決めます.
