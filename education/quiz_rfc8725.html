Q1: Does RFC 8725 make JWT BCP sufficient for A2A authorization?

Multiple Choice

An A2A profile cites RFC 8725 and claims that using JWT BCP automatically settles peer acceptance and authorization.

**Explanation:** A: Sections 2-3 defines the mechanism, not all relying-party policy; the conclusion overclaims its effect. B: Sections 2-3 supports the mechanism statement, while the application still owns the stated policy boundary. C: A relationship to another specification does not transfer that specification's guarantees or local policy automatically. D: RFC 8725 still defines interoperable behavior within its scope; calling it guidance does not make processing arbitrary.

Q2: Two implementations reach incompatible results for JWT BCP. What must the profile define?

Multiple Choice

D: Two locally successful but unequal outputs are not interoperable merely because both implementations accept themselves.

Q5: Which review response is justified when JWT BCP is used at an A2A trust boundary?

Multiple Choice

Intended use: when an API gateway, authorization server, or service validates JWTs from more than one source. Observed defect: algorithm confusion, cross-JWT confusion, weak keys, and accepting tokens for the wrong audience.

**Explanation:** A: A mechanism's purpose does not establish that this instance or context is acceptable. B: Correct construction is necessary but not sufficient for verification and local acceptance. C: An adjacent specification cannot convert a failed or context-confused result into success. D: Section 2 supports resolving the defect before relying on the result. The profile rule is: use explicit typing, separate token kinds, short lifetimes, and unambiguous issuer and audience values. The check is: pin acceptable algorithms and keys to the issuer and token kind before processing claims. The local policy is: the profile that says which token kind and claims are acceptable at this endpoint.
