Q1: このCBOR itemはA2A operationに受理可能か

Multiple Choice

decoderはwell-formedかつvalidなCBOR text stringをacceptします.A2A operation schemaはinteger key 1と2を含むmapを要求します.

**Explanation:** A: Section 5はvalid CBORと特定application protocolがexpectedするinputを区別します. B: 正解です.Sections 5 and 5.3はwell-formedness,validity,application expectationを連続するcheckとして扱います. C: Text stringはbasic CBOR data typeです.defectはCBOR syntaxではなくschema mismatchです. D: UTF-8 validityはtext stringをoperation-required mapへ変えません.

Q2: RFC 8949はすべてのCBOR messageにcore deterministic encodingを要求するか

Multiple Choice

A2A telemetry messageはdata-model valueへdecodeするだけで,encoded bytesのhash/signatureやbyte-for-byte comparisonをしません.profileはdeterministic encodingを選んでいません.

**Explanation:** A: Section 4.1はpreferred serializationが一般にrequiredではないとし,Section 4.2が必要なprotocol向けdeterministic variantを定義します. B: CBORは通常,一つのdata-model valueに複数のwell-formed encodingを許します. C: Deterministic encodingはitemがtagを持つかとは独立です. D: 正解です.profileはSection 4.2.1のcore requirementsやSection 4.2.3のspecified alternativeを選べます.

Q3: authorization parserはこのmapをどう扱うべきか

Multiple Choice

attackerはroleを二回含むCBOR mapを送り,role=readerの後にrole=adminを置きます.gateway libraryは最初を保持し,backend libraryは最後を保持します.profileはauthorizationに一つのunambiguous role valueを要求します.

**Explanation:** A: Section 5.3.1はduplicate map keyをvalidity errorとし,decoder behaviorが異なることを説明します. B: CBOR mapはupdate logではなく,generic data modelはunique keyを持ちます. C: 正解です.Sections 5 and 5.3.1はCBOR-based protocolにhandlingを定義させ,このsecurity profileにはsingle interpretationが必要です. D: Divergent native behaviorはpremiseにあるcross-component security failureを作ります.

Q4: なぜimplementation間でsignature verificationが失敗するか

Multiple Choice

二つのA2A implementationは同じmapをlocalにre-encodeしてCBOR-encoded request bytesへsignします.一方はSection 4.2.1 core deterministic encoding,他方はSection 4.2.3 length-first map orderingを使います.profileはdeterministic CBORとだけ書き,identical signature inputを要求します.

**Explanation:** A: Sections 4.2.1 and 4.2.3は意図的に異なるmap orderingを定義します.byte-signing profileは一つを選びsigning inputを定義します. B: 各variantは自身のrule内でdeterministicですが,二variantが同じbytesを作るとは限りません. C: Message timingはどちらのdeterministic encodingにも含まれず,interoperability ruleを修復しません. D: Cryptographic signatureはdefined bytesを対象とし,signatureをdecodeしてもsigned inputは変わりません.

Q5: parser-availability criterionを満たす設計はどれか

Multiple Choice

unauthenticated A2A endpointがwell-formed CBORをacceptします.2 KBのinputが巨大lengthを宣言したり,decoderのmemory/stackが尽きるまでarrayを深くnestできます.requirementはauthentication前のbounded workです.

**Explanation:** A: Section 10はlarge size/deep nestingでresourceをexhaustするhostile well-formed inputを説明します. B: Section 10はTLS,signing,その他trustedと想定するsourceの後でもinputをhostileとして扱うよう述べます. C: Early attacker-driven allocationはbounded-work criterionに反し,schema validation前にfailureします. D: Section 10はlarge data item,stack exhaustion,integer issue,superlinear workにappropriate resource managementを求めます.exact limitはprofile/implementation policyです.

Q6: A2A profileはidempotency keyをどう定義すべきか

Multiple Choice

agentはrequest_id=SHA-256(encoded CBOR)を計算します.gatewayは同じdata-model valueをdecodeし,別のvalid representationへre-encodeしてbackendへ送り,backendがrequest_idを再計算します.profileはこのgatewayを越えたsemantically identical requestに同じIDを要求します.

**Explanation:** A: Sections 4.1 and 4.2はdata-model equalityとdeterministic byte representationを区別します. B: 指定cross-gateway identity criterionを満たします.Sections 4.2 and 5.6のencoding/map-key choiceをA2A profileで明示します. C: 事後に二IDを同一視するとreplay/authorization checkがambiguousになります. D: TagはCBORをidentifyしますが,content encodingをnormalizeしません.
