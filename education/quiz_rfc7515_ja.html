参照仕様

  • RFC 7515: JSON Web Signature

Q1: validなJWSがcryptographically protectするものはどれ?

単一選択
**解説:** coverされるのはJWS signing inputであり任意のenclosing dataではない. signatureまたはMACはprotected-headerとpayloadのrepresentationに対して計算する. cryptographic integrityだけではapplication claimを受理してよいか決まらない.

Q2: security-relevantなJOSE header parameterのintegrityが必要な場合どこに置く?

単一選択
**解説:** Protected Headerのbyteはsigning inputに含まれる. Unprotected Header parameterはintegrity protectedではない. outer objectはapplicationがsigned payloadへ明示的に含めない限りcoverされない.

Q3: JWSの"kid" header parameterのroleはどれ?

単一選択
**解説:** key identifierだけではownershipやtrustを確立しない. algorithm policyとkey identificationは別のdecisionである. RFC 7515はkidをhintと定義しstructureをspecifiedしない.

Q4: JWSがmathematicalにはverifyできるがlocal policyでdisabledなalgorithmを使う. 受理すべき?

単一選択
**解説:** RFC 7515はalgorithmがapplicationにacceptableであることを要求する. JWSはcryptographic validationとapplication acceptance checkの両方を通って初めてvalidになる. key hintはdisallowed algorithmをauthorizeしない.

Q5: protected headerに"crit"で列挙されたextensionがありverifierは理解できない. どうする?

単一選択
**解説:** critでnamedされた全parameterを理解し処理する必要がある. unknown critical parameterのignoreはcritの目的を損なう. verifierはsigning inputを壊さずsenderのprotected headerを書換えられない.

Q6: Compact SerializationとJSON Serializationを区別するstatementはどれ?

単一選択
**解説:** Compact SerializationにはJWS Unprotected Headerがない. multiple signatureはgeneral JSON serializationが提供する. これらはcompact formではなくJWS JSON serializationのcapabilityである.

Q7: general JWS JSON objectが3つのsignatureを持ちapplicationは特定2 signerを要求する. どのvalidation ruleを使う?

単一選択
**解説:** RFC 7515は少なくとも1つを要求するがapplicationは特定または複数signatureを要求できる. どのsignature valueをvalidate必須にするかapplicationが決めbase minimumより増やせる. array positionはapplicationのsigner policyを定義しない.

Q8: verifierが"jku" URLからJWK Setを取得する. なおrequiredなcheckはどれ?

単一選択
**解説:** RFC 7515はintegrity-protectedな取得とTLS server identity validationを要求する. hintのmatchだけではtrusted key sourceを確立しない. attacker-controlled key sourceならmatching keyとsignatureを提供できる.

Q9: Agent CardのJWS validation成功だけでは確立しないものはどれ?

単一選択
**解説:** これはsuccessful validationのcore cryptographic resultである. Protected Header contentはsigning inputに参加する. authority, issuer binding, audience, freshnessにはapplication-profile ruleが必要である.

Q10: RFC 7515から導けるreview conclusionはどれか

単一選択

Agent Card wrapperにvalidなJWSとunsignedな`target`, `valid-until` memberがあります. signed payloadはagentを識別しますが, gatewayは外側の2 memberでroutingとauthorizationを判断します. expected keyとalgorithmによるvalidationは成功しました.

**解説:** RFC 7515 Section 5.2がsignatureをvalidateする対象はJWS Signing Input, つまりencoded protected headerとpayloadです. JWSに隣接するだけのJSON memberはそのinputに入りません. validation後に移動またはcopyしても, signerがcoverしたbyteは変わりません. application profileはroutingやauthorizationの意味を持つfieldを決め, signing前にintegrity-protected contentへ置き, acceptable algorithmとtrusted keyを定義する必要があります. Section 5.2ではcryptographic validationが成功しても, algorithm acceptabilityはapplication decisionです. JWS validationだけではclaim semanticsやfreshnessも決まりません. RFC 7515 Section 10.10はreplay protectionをapplication concernとして扱い, 例としてunique message identifierをsigned contentへ入れprior useを確認する方法を示します. したがってvalid signatureはsigned assertionには必要ですが, このwrapperのacceptanceには十分ではありません.
