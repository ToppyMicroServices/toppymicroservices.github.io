Q1: A good Security Considerations section should primarily

Multiple Choice
**Explanation:** A Security Considerations section is not a formality added after the protocol is designed. It should let implementers and users understand the relevant threats and the limits of the design. **Terms:** A **Security Considerations section** connects the protocol to its security properties, threats, failure modes, assumptions, and countermeasures. **Correct (B):** RFC 3552 says the section should inform readers of relevant security issues and clearly describe foreseeable threats, protections, and residual risks. **Options:** - A (incorrect): Repeating the protocol does not identify its security consequences. - B (correct): Realistic threats, assumptions, and mitigations give readers information they can act on. - C (incorrect): No protocol is simply “secure” in every threat model. The section must state scope and limitations. **Related:** The useful question is not “does the document claim security,” but “under which assumptions does it provide which protections.”

Q2: Useful items to include are (select all)

Multi-Select
**Explanation:** RFC 3552 calls for analysis tied to the protocol, including its threat environment, the security properties it provides, and residual risks. **Terms:** **In scope** identifies attacks the design considers. **Protection properties** say what cryptography or another mechanism actually provides. **Residual risk** is what can still go wrong after mitigation. **Correct (A,B,C):** RFC 3552 calls for the scope of attacks, the portions and properties protected by security mechanisms, and a clear description of remaining risk. **Options:** - A (correct): Readers need to know which attacks are considered and which are excluded, including why. - B (correct): Saying only that data is “protected” is insufficient; the document should distinguish confidentiality, integrity, authentication, and related properties. - C (correct): Mitigation does not erase all risk, so the remaining exposure must be stated. - D (incorrect): Compliance marketing is not a substitute for security analysis. **Related:** Operational and privacy guidance can still be valuable when relevant, but those topics should not be presented as RFC 3552's specific checklist when the document does not say so.

Q3: Your draft says "This protocol has no security considerations". A better approach is to

Multiple Choice
**Explanation:** A small protocol change can still create risk through deployment, composition, or misuse. An unsupported “no considerations” statement hides those assumptions. **Terms:** An **assumption** is a condition on which the analysis depends. **Residual risk** is exposure that remains after the stated countermeasures. **Correct (A):** If the impact is genuinely limited, explain why, identify the assumptions, and state what the protocol does not address. **Options:** - A (correct): It gives readers enough information to test whether the conclusion applies to their deployment. - B (incorrect): An external reference cannot replace analysis of this protocol's interactions and assumptions. - C (incorrect): Generic controls do not explain which threats arise from this protocol or what remains exposed. **Related:** RFC 3552 requires due diligence about known or foreseeable threats, even though no protocol must be immune to every attack.

Q4: A Security Considerations section says only "Use strong cryptography." Which revision makes the guidance reviewable

Multiple Choice
**Explanation:** **Terms:** A reviewable security analysis states what is protected and which security properties are required, describes attacker capabilities and trust assumptions, explains key management, and identifies residual risk after mitigation. **Correct (B):** This revision supplies the claims and boundary conditions a reviewer needs to test. It connects mechanisms to protected assets, threats, operational assumptions, and risks the design does not eliminate. **Options:** - A (incorrect): Algorithm names alone do not establish the required security properties, threat model, key lifecycle, or deployment assumptions. - B (correct): Each listed element makes the protection claim specific enough to assess against the intended deployment. - C (incorrect): A cipher suite does not by itself address authentication, key management, endpoint compromise, availability, or every deployment model. **Related:** RFC 3552 requires the services expected from a lower-layer security protocol and the resulting combined-system properties to be specified, and calls for a clear description of residual risk.

Q5: When discussing mitigations, good guidance tends to (select all)

Multi-Select
**Explanation:** A list of countermeasure names is not enough for an implementer to decide whether a mitigation fits a deployment. **Terms:** A **mitigation** reduces a threat; a **trade-off** is its performance, complexity, or operational cost; **out of scope** identifies what the mitigation is not intended to solve. **Correct (A,B,C):** Useful guidance explains the defended threat, the cost or constraints, and the remaining limits. **Options:** - A (correct): Without the threat, readers cannot evaluate whether the mitigation is relevant. - B (correct): Costs and constraints affect whether a countermeasure can be deployed correctly. - C (correct): Explicit limits show where another control or a different threat model is needed. - D (incorrect): RFC 3552 explicitly does not require immunity to every form of attack. **Related:** A mitigation can be valuable without being complete. Clear residual-risk text prevents it from being mistaken for a guarantee.

Q6: Name the concept that describes assumed attackers and capabilities (two words)

Short Text
**Explanation:** The first step in reading security text is to identify who the attacker is assumed to be and what that attacker can do. **Real-world usage:** Protocol reviews and incident analysis use the threat model to decide whether a mitigation covers the attacker and deployment in question. **Terms:** A **threat model** describes attacker capabilities, available resources, relevant assets, trust assumptions, and explicit exclusions. **Correct:** **threat model**. **Why this matters:** A countermeasure that is adequate against passive observation might fail against an active attacker who can insert, delete, or modify messages. **Related:** RFC 3552 uses the threat model both to identify attacks of concern and to state which attacks are explicitly out of scope.

Q7: How should “log everything for security” be turned into useful Security Considerations

Multiple Choice

To investigate misuse between agents, a design proposes long-term retention of complete requests, session proofs, and task context.

**Explanation:** RFC 3552 asks authors to explain a threat model and the resulting security properties, not merely name a mechanism. Logging can support attack detection, but it can also create a high-value data set, a tampering target, and a resource-exhaustion path. - A (incorrect): Authentication addresses only part of access. Excess privilege, credential compromise, exfiltration, log injection, deletion, storage exhaustion, retention, and remaining risk are still unanalyzed. - B (incorrect): RFC 3552 does not require immunity to every attack; it asks authors to explain threats, countermeasures, exclusions, and residual risk. A blanket prohibition does not evaluate the operational trade-off. - C (correct): Stating what the log detects, what must be protected, what attackers can do, and what remains after controls gives implementers a reviewable security argument. In this sense, “treat logging as an attack” is too compressed. The precise design rule is to **include log collection as an attack surface and privacy-sensitive asset in the threat model**. Field selection, avoidance of raw values, retention, access control, redaction, tamper evidence, and failure behavior then belong to the deployment design.
