Q1: In one sentence, the Forwarded header is used to

Multiple Choice
**Explanation:** `Forwarded` records information that may otherwise be changed or lost as an HTTP request passes through proxies. It does not secure the connection or authenticate the recorded values. A deployment should define which intermediaries may add or replace this field before using it for security-sensitive decisions. A: This describes the field's purpose: conveying information about the request and the forwarding proxies. B: TLS provides transport security; `Forwarded` is an HTTP metadata field and does not replace it. C: A sender can supply false field values, so authenticity depends on a defined proxy trust boundary.

Q2: Which parameter names are defined by RFC 7239 for a Forwarded element? (Select all that apply.)

Multi-Select
**Explanation:** RFC 7239 initially registers four parameters. Extensions can define additional parameters, but `path` and `port` are not among these four. A: `for` identifies the node that made the request to the proxy. B: `by` identifies the proxy's interface that received the request. C: `proto` records the protocol used for the request received by the proxy. D: `host` records the original Host request-header value received by the proxy. E: `path` is not an RFC 7239 parameter; the request path is outside the initial parameter set. F: `port` is not a separate RFC 7239 parameter; a node identifier can include a port where the syntax permits it.

Q3: How are multiple proxies represented in Forwarded

Multiple Choice
**Explanation:** A forwarded-element contains the information added by one proxy. Multiple elements form an HTTP list in the order in which the field was generated. A parser also has to handle quoted strings and optional whitespace according to the field grammar. A: Separate field lines are allowed to be combined, but commas remain the list delimiter and are not forbidden. B: Commas separate forwarded-elements; semicolons separate parameters within one element. C: RFC 7239 defines HTTP field-value grammar, not a JSON representation.

Q4: A key operational risk with Forwarded is

Multiple Choice
**Explanation:** RFC 7239 Section 8.1 states that `Forwarded` cannot be relied upon to be correct because any node, including the client, can modify it. A common boundary design is to remove untrusted forwarding fields at the edge and generate values from observations made by trusted proxies. A: The field does not negotiate an HTTP version and therefore does not force an HTTP/2 downgrade. B: The field does not alter an HSTS policy or disable HTTPS upgrading. C: Trusting an untrusted sender's value can let that sender spoof client or proxy metadata.

Q5: Which parameter name typically identifies the client that initiated the request (one token)

Short Text
**Explanation:** The token is **for**. It identifies the node that made the request to the proxy, whereas `by` identifies the proxy interface that received it. Its value can be an IP-based node identifier, `unknown` when the preceding node is not known, or an obfuscated identifier when exposing the real identifier is undesirable.

Q6: Why might a deployment use an obfuscated identifier instead of an IP address in the for parameter?

Multiple Choice
**Explanation:** RFC 7239 permits an obfuscated node identifier when the real identifier should not be disclosed. Such an identifier begins with an underscore and ought to be randomly generated per request unless correlation is intentionally required. The literal `unknown` has a different meaning: it is used when the identity of the preceding node is not known. A: Obfuscation can limit disclosure while retaining only the correlation a deployment deliberately needs. B: Obfuscation does not authenticate any proxy or prove the provenance of the field. C: The mechanism is defined for identifier disclosure and correlation policy, not as header compression.
