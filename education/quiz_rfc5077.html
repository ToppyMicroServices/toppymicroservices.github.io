Q1: A TLS session ticket is primarily used to

Multiple Choice
**Explanation:** A server places the state needed for resumption, including the master secret and negotiated parameters, in a ticket that it encrypts and integrity-protects. The client stores the opaque ticket and presents it in a later ClientHello. **Options:** - A (incorrect): A ticket does not replace certificate or endpoint validation in the handshake that establishes the session. - B (incorrect): Session tickets operate inside TLS and do not enable plaintext HTTP. - C (correct): Returning protected state to the client lets the server resume without retaining a per-client session-cache entry.

Q2: Who protects the confidentiality and integrity of the ticket contents

Multiple Choice
**Explanation:** The ticket is opaque to the client. The server creates it with confidentiality and integrity protection under secret ticket-protection keys, and later decrypts and validates it before using the recovered state. **Options:** - A (incorrect): The client stores and returns the ticket; it does not encrypt the server's session state with a client private key. - B (correct): Ticket construction, protection, validation, and key management are server responsibilities. - C (incorrect): DNSSEC protects DNS data and has no role in signing a TLS session ticket.

Q3: A major operational risk of long lived ticket keys is

Multiple Choice
**Explanation:** A ticket can contain the TLS master secret. As an operational inference, compromise of a long-lived ticket-protection key can expose state in captured tickets and, for affected TLS versions and configurations, enable decryption of associated recorded resumed traffic. This is why RFC 5077 recommends changing ticket keys regularly. **Options:** - A (correct): It captures the possible backward-looking impact while correctly making it conditional on the TLS construction. - B (incorrect): Previously issued tickets protected by the compromised key can also be affected. - C (incorrect): Ticket-protection keys are separate from the certificate, and RFC 5077 recommends changing them regularly.

Q4: Good hygiene for session tickets includes (select all)

Multi-Select
**Explanation:** Stateless resumption replaces per-session server storage with protected client-held state and server-side key management. A cluster must make an explicit choice about the lifetime and the nodes that can decrypt a ticket. **Options:** - A (correct): RFC 5077 recommends changing ticket-protection keys regularly and when the format or algorithms change. - B (correct): The server controls acceptable lifetime based on the deployment's operational and security requirements. - C (correct): Cross-node acceptance requires the relevant servers to have access to compatible protection keys, with the resulting sharing risk managed. - D (incorrect): Ticket keys are server secrets; exposing them to client storage would destroy the protection boundary.

Q5: A difference between server side session caches and tickets is

Multiple Choice
**Explanation:** A stateful session cache retains an entry for each resumable session. A ticket moves that state into a client-held opaque value, while the server retains the smaller set of keys needed to protect and recover ticket contents. **Options:** - A (incorrect): The state placement is reversed: a cache stores per-session server entries, while a ticket moves that state to the client. - B (correct): It states the storage-versus-key-management tradeoff that distinguishes stateless tickets. - C (incorrect): The server still needs a key to protect the confidentiality and integrity of ticket contents.

Q6: What do you call the encrypted blob the client stores to resume a TLS session

Short Text
**Explanation:** **Correct:** **ticket** or **session ticket**. RFC 5077 defines the ticket as an opaque structure that carries session-specific state. The client must not inspect it under an assumed internal format; it stores the value and presents it in the `SessionTicket` extension when requesting resumption.
