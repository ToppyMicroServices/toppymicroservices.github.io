Q1: Which request header carries Basic credentials

Multiple Choice
**Explanation:** A Basic challenge is carried in `WWW-Authenticate`; the client's credential response uses the `Authorization` request header. The client sends `Authorization: Basic <token68>`. `Authorization` is the HTTP authentication framework's request field for credentials. There is no `Authenticate` request field; server challenges use `WWW-Authenticate`. `Cookie` is a separate state mechanism and is not the Basic credential field. Proxy authentication uses `Proxy-Authorization` rather than `Authorization`.

Q2: Basic credentials are encoded as

Multiple Choice
**Explanation:** Basic forms `user-pass` by concatenating the user-id, one colon, and the password, converts that character sequence to octets, and Base64-encodes the octets. Base64 changes the representation but supplies no confidentiality. The transmitted Basic token is not a password hash; the original user-pass octets can be recovered from Base64. Basic does not encrypt the credential with the server's public key. This describes the required construction while keeping the character-encoding step distinct. The default character encoding is not universally fixed; a challenge can advertise `charset="UTF-8"`.

Q3: Why is Basic authentication unsafe without TLS

Multiple Choice
**Explanation:** Base64 is a reversible binary-to-text encoding. It is not encryption and does not require a secret key to decode. A passive observer can recover the user-id and password from an unprotected Basic credential. Basic operates in HTTP's authentication semantics and is not inherently incompatible with HTTP/2. TLS or another external secure channel is needed to protect the credential in transit. Basic does not itself force browser cookies to be sent across sites. Password reuse increases the impact because disclosure can compromise accounts outside the challenged protection space.

Q4: Which status code commonly triggers a Basic auth challenge

Multiple Choice
**Explanation:** An origin server can challenge with `401 Unauthorized` and a `WWW-Authenticate: Basic realm=...` response field. 401 is the standard status used for this origin authentication challenge. It tells the client that credentials are required for the selected protection space. 206 reports a partial-content response and does not initiate Basic authentication. 302 redirects the request; it is not the authentication challenge status. A proxy uses 407 and `Proxy-Authenticate`, which is a separate exchange.

Q5: A common operational best practice for Basic auth credentials is

Multiple Choice
**Explanation:** A Basic credential is a reusable secret. TLS protects it in transit to the intended peer but does not make later logs or forwarding safe. Restricting its destination and excluding it from logs reduces accidental disclosure outside the intended protection space. Credentials placed in a URL can spread through histories, access logs, analytics, and other URI-processing systems. Logging the decoded user-pass stores the reusable secret in another system and broadens access to it. Trust-boundary filtering and secret-aware logging address two common operational leakage paths. RFC 7617 defines when credentials may be reused within an authentication scope; it does not make arbitrary cross-origin forwarding safe.

Q6: Which Basic challenge parameter advertises that the server expects UTF-8 for user-pass (one word)

Short Text
**Explanation:** The optional **charset** authentication parameter appears in a Basic challenge. Its only defined value in RFC 7617 is `UTF-8`, matched case-insensitively. The parameter is advisory and addresses the character-to-octet encoding used before Base64. It is not an encryption setting and does not appear inside the credential token. Without an agreed character encoding, non-ASCII user-ids and passwords can produce interoperability failures.

Q7: Which credential-handling decision is best supported by RFC 7617?

Multiple Choice

An agent authenticates with Basic over HTTPS to `https://api.example/tasks/7`. The origin returns a redirect to `https://collector.example/import`. A client library would forward the same `Authorization` field and record its decoded value in a debug log.

**Explanation:** RFC 7617 Section 2.2 allows preemptive reuse only for resources within the authentication scope of the protection space. Its examples treat a scheme change as outside that scope; a different authority is not the original origin's protection space either. A redirect does not grant the new origin permission to receive the credential. Section 4 explains that Basic transmits a password in readily reversible form and should not protect sensitive information without HTTPS. Base64 re-encoding supplies no freshness or confidentiality. Because the value remains a reusable secret, recording the decoded form creates another disclosure path; avoiding that log is a deployment consequence of the threat, not a separate wire-format rule stated by RFC 7617. The new origin can issue its own applicable challenge, or an application can apply an explicit credential policy. It must not acquire the first origin's credential merely through redirect handling.
