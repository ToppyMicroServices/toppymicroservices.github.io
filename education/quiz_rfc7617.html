Q1: Which request header carries Basic credentials

Multiple Choice
**Explanation:** **Terms:** A Basic challenge is carried in `WWW-Authenticate`; the client's credential response uses the `Authorization` request header. **Correct (A):** The client sends `Authorization: Basic `. **Options:** - A (correct): `Authorization` is the HTTP authentication framework's request field for credentials. - B (incorrect): There is no `Authenticate` request field; server challenges use `WWW-Authenticate`. - C (incorrect): `Cookie` is a separate state mechanism and is not the Basic credential field. **Related:** Proxy authentication uses `Proxy-Authorization` rather than `Authorization`.

Q2: Basic credentials are encoded as

Multiple Choice
**Explanation:** **Terms:** Basic forms `user-pass` by concatenating the user-id, one colon, and the password, converts that character sequence to octets, and Base64-encodes the octets. **Correct (C):** Base64 changes the representation but supplies no confidentiality. **Options:** - A (incorrect): The transmitted Basic token is not a password hash; the original user-pass octets can be recovered from Base64. - B (incorrect): Basic does not encrypt the credential with the server's public key. - C (correct): This describes the required construction while keeping the character-encoding step distinct. **Related:** The default character encoding is not universally fixed; a challenge can advertise `charset="UTF-8"`.

Q3: Why is Basic authentication unsafe without TLS

Multiple Choice
**Explanation:** **Terms:** Base64 is a reversible binary-to-text encoding. It is not encryption and does not require a secret key to decode. **Correct (B):** A passive observer can recover the user-id and password from an unprotected Basic credential. **Options:** - A (incorrect): Basic operates in HTTP's authentication semantics and is not inherently incompatible with HTTP/2. - B (correct): TLS or another external secure channel is needed to protect the credential in transit. - C (incorrect): Basic does not itself force browser cookies to be sent across sites. **Related:** Password reuse increases the impact because disclosure can compromise accounts outside the challenged protection space.

Q4: Which status code commonly triggers a Basic auth challenge

Multiple Choice
**Explanation:** **Terms:** An origin server can challenge with `401 Unauthorized` and a `WWW-Authenticate: Basic realm=...` response field. **Correct (A):** 401 is the standard status used for this origin authentication challenge. **Options:** - A (correct): It tells the client that credentials are required for the selected protection space. - B (incorrect): 206 reports a partial-content response and does not initiate Basic authentication. - C (incorrect): 302 redirects the request; it is not the authentication challenge status. **Related:** A proxy uses 407 and `Proxy-Authenticate`, which is a separate exchange.

Q5: A common operational best practice for Basic auth credentials is

Multiple Choice
**Explanation:** **Terms:** A Basic credential is a reusable secret. TLS protects it in transit to the intended peer but does not make later logs or forwarding safe. **Correct (C):** Restricting its destination and excluding it from logs reduces accidental disclosure outside the intended protection space. **Options:** - A (incorrect): Credentials placed in a URL can spread through histories, access logs, analytics, and other URI-processing systems. - B (incorrect): Logging the decoded user-pass stores the reusable secret in another system and broadens access to it. - C (correct): Trust-boundary filtering and secret-aware logging address two common operational leakage paths. **Related:** RFC 7617 defines when credentials may be reused within an authentication scope; it does not make arbitrary cross-origin forwarding safe.

Q6: Which Basic challenge parameter advertises that the server expects UTF-8 for user-pass (one word)

Short Text
**Explanation:** **Terms:** The optional **charset** authentication parameter appears in a Basic challenge. Its only defined value in RFC 7617 is `UTF-8`, matched case-insensitively. **Correct:** **charset**. **Why this matters:** The parameter is advisory and addresses the character-to-octet encoding used before Base64. It is not an encryption setting and does not appear inside the credential token. **Related:** Without an agreed character encoding, non-ASCII user-ids and passwords can produce interoperability failures.
