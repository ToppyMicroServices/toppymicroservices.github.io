Q1: What is the main purpose of HPACK in HTTP/2

Multiple Choice
**Explanation:** **Terms:** HPACK represents HTTP/2 header fields as indexed references or literals. Its static table is fixed by the specification; its dynamic table is synchronized for a connection. **Correct (B):** Reusing table entries and compact literal encodings reduces repeated header bytes, which is HPACK's purpose. **Options:** - A (incorrect): HPACK can reduce the encoded size of a header block, but it does not encrypt header fields; transport confidentiality is a separate concern. - B (correct): Indexed and literal representations remove redundancy while allowing the decoder to reconstruct the same ordered header list. - C (incorrect): HPACK does not authenticate the server or replace certificate validation. **Related:** HTTP/3 uses QPACK, whose table synchronization is adapted to QUIC's stream delivery model.

Q2: Which table is shared state that changes over time on a connection

Multiple Choice
**Explanation:** **Terms:** The static and dynamic tables share one index address space, but only the dynamic table is updated by encoder instructions. **Correct (C):** Entries are inserted into and evicted from the dynamic table as header blocks are encoded and decoded. **Options:** - A (incorrect): The static table's entries and indices are fixed by RFC 7541 and do not evolve with traffic. - B (incorrect): A DNS cache is not part of HPACK's encoding or decoding context. - C (correct): The encoder and decoder maintain matching connection-specific dynamic-table state. **Related:** If their dynamic-table state diverges, indexed references can decode to the wrong field or produce a compression error.

Q3: Which example values contain reusable credential or session material and therefore warrant a never-indexed representation (select all)

Multi-Select
**Explanation:** **Terms:** A literal header field marked **never indexed** is intended for values that should not be inserted into a compression table. RFC 7541 uses credentials and cookies as examples of sensitive fields. **Correct (A,C,D):** These example values carry bearer or session material that can be reused if exposed. **Options:** - A (correct): A bearer token is a reusable credential, so retaining it in compression state increases exposure. - B (incorrect): This media-type preference is not a credential or session identifier in the stated example. - C (correct): A session cookie can authorize later requests and should be treated as secret material. - D (correct): A response that sets a session identifier carries the same kind of reusable secret. **Related:** Sensitivity is a property of the value and threat model. A field name alone is not a universal rule for every deployment.

Q4: In HTTP/2, what bounds the maximum HPACK dynamic-table size an encoder may use

Multiple Choice
**Explanation:** **Terms:** In HTTP/2, the decoder advertises a maximum with **SETTINGS_HEADER_TABLE_SIZE**. The encoder can choose a smaller current size but cannot exceed that bound. **Correct (A):** The acknowledged setting is the protocol-defined maximum for the encoder's dynamic table. **Options:** - A (correct): It lets the decoder bound persistent compression state and therefore its memory commitment. - B (incorrect): The static table is a separate fixed table; its entry count does not bound the dynamic table. - C (incorrect): A header block can span frames, and frame payload size is not the dynamic-table capacity limit. **Related:** The encoder signals a chosen lower size with a dynamic table size update at the start of a header block.

Q5: Which named static code can HPACK use for string literals (one word)

Short Text
**Explanation:** **Terms:** A string literal carries a flag indicating whether its octets use HPACK's fixed **Huffman** code. **Correct:** **Huffman**. **Why this matters:** RFC 7541 defines one static table in Appendix B, so the code is not learned or negotiated per connection. The decoder must also validate padding and the end-of-string rules. **Related:** Huffman coding of a literal is separate from whether the resulting header field is indexed in the dynamic table.

Q6: A classic risk when compressing secrets together with attacker influenced data is

Multiple Choice
**Explanation:** **Terms:** A **compression oracle** exists when an attacker can influence part of the input and observe how encoded length changes relative to a secret in the same compression context. **Correct (C):** Repeated length observations can reveal whether an attacker-controlled guess shares structure with the secret. **Options:** - A (incorrect): The side channel leaks information through size behavior; HPACK does not place TLS traffic keys into header blocks. - B (incorrect): TLS can still authenticate the encrypted record; authenticated transport does not remove information exposed through a length oracle. - C (correct): This is the probing risk described in RFC 7541's security considerations. **Related:** Never-indexed representations and separating compression contexts reduce some risks, but the design still needs an explicit attacker-influence analysis.
