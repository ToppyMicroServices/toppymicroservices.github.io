Q1: browserへHSTS policyを伝えるheaderはどれ

Multiple Choice
**Explanation:** conformingなuser agentは, underlying security errorのないsecure transportで受け取った`Strict-Transport-Security` response fieldだけを処理します. このfieldは必須の`max-age`と, 任意の`includeSubDomains`を運びます. **選択肢:** - A (incorrect): `Transport-Security` は標準 header 名ではありません. - B (correct): `Strict-Transport-Security` がHSTS policyを伝えるfieldです. - C (incorrect): `Secure-Only` はHSTS response fieldの名前ではありません.

Q2: RFC 6797がStrict-Transport-Security用に定義するdirectiveはどれ (複数選択)

Multi-Select
**Explanation:** RFC 6797は必須directiveの`max-age`と, 任意directiveの`includeSubDomains`を定義しています. user agentは, fieldの他の部分が有効なら未知のdirectiveを無視して認識済みdirectiveを処理します. **選択肢:** - A (correct): `max-age` はpolicy lifetimeを秒で指定し, field grammar上必須です. - B (correct): `includeSubDomains` はpolicyをsubdomainへ任意に広げます. - C (incorrect): `preload` はRFC 6797が定義するdirectiveではなく, browserのpreload登録は別の運用mechanismです. - D (incorrect): `allowInsecure` はRFC 6797のdirectiveではなく, HSTSの目的にも反します.

Q3: HSTSだけでは完全に守れない状況として典型なのはどれ

Multiple Choice
**Explanation:** secure transport上のHTTP responseから学習するHSTS policyは, それより前のinsecureなfirst contactを保護できません. user agentがhostをKnown HSTS Hostとして記録する前なら, active attackerが通信へ介入できます. **選択肢:** - A (incorrect): unexpiredなpolicyがcache済みなら, user agentはそのhostへsecure transportを強制します. - B (incorrect): 学習済みpolicyの`includeSubDomains`は, matchingするsubdomainへenforcementを広げます. - C (correct): prior policyのないbootstrap requestには弱さが残ります. preloaded Known HSTS Host listはこのbootstrap gapを緩和できますが, RFC 6797は`preload` header directiveを定義していません.

Q4: max-ageの単位は何

Multiple Choice
**Explanation:** `max-age`は`delta-seconds` grammarを使い, fieldを受信してからの秒数を1桁以上のdecimal digitで表します. 後で有効なfieldを受け取ると, policy expiryはその受信時刻を基準に更新されます. **選択肢:** - A (correct): RFC 6797 の `max-age` は秒単位です. - B (incorrect): minutesで考えたdurationも秒へ変換して指定します. - C (incorrect): daysで考えたdurationも秒へ変換して指定します.

Q5: policyを全subdomainへ適用するdirectiveは何 (token 1つ)

Short Text
**Explanation:** **Correct:** **includeSubDomains**. この任意かつvaluelessなdirectiveは, 発行hostからsubdomainへHSTS policyを広げます. assertする前に, insecure HTTP serviceへ依存するsubdomainを確認しないと, conformingなuser agentからそのserviceへ到達できなくなる可能性があります.

Q6: HSTSを安全に導入する時, 典型の第一歩として近いのはどれ

Multiple Choice
**Explanation:** user agentはHSTS policyを`max-age` expiryまでcacheし, 後で有効なfieldを受け取るとexpiryを更新します. そのため短いlifetimeから始めてdeploymentを観測するのは保守的なrollout practiceです. RFC 6797がこの順序をnormative requirementとして定めているわけではありません. **選択肢:** - A (incorrect): 最初から巨大 `max-age` と `includeSubDomains` を入れると, 未準備 subdomain を巻き込んで破壊的になり得ます. - B (correct): 短い初期lifetimeならpersistenceを抑えつつ, certificate, redirect, subdomainの問題をmonitorできます. - C (incorrect): conformingなuser agentはinsecure transportで受け取ったSTS fieldを無視します.
