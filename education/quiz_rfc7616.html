Q1: Digest authentication aims to avoid sending

Multiple Choice
**Explanation:** Digest computes a response from values including the username, password-derived secret, server nonce, HTTP method, and request URI. The client sends a computed Digest response instead of placing the password itself on the wire in clear form. A password-derived Digest response is not a complete secure channel, and the server-side H(A1) value is itself sensitive credential material. A: Digest still uses HTTP headers, including `WWW-Authenticate` for the challenge and `Authorization` for the response. B: Avoiding clear-form password transmission is a central improvement over Basic authentication. C: HTTP status codes remain part of the exchange; a challenge commonly arrives with 401.

Q2: Which response header carries a Digest challenge

Multiple Choice
**Explanation:** A server that lacks an acceptable credential response sends a 401 response with a `WWW-Authenticate: Digest ...` challenge. `WWW-Authenticate` carries the server's Digest challenge parameters. Proxy authentication uses the parallel `Proxy-Authenticate` and `Proxy-Authorization` fields. A: It is the response header that identifies the scheme and supplies values such as `realm`, `nonce`, and `algorithm`. B: `Authorization` is the request header the client uses for its computed Digest response. C: `Forwarded` describes proxy-related request information and does not carry an authentication challenge.

Q3: In Digest, a nonce is primarily used to

Multiple Choice
**Explanation:** A **nonce** is an opaque server-specified challenge value. Its generation and validity policy can limit when or where a captured response is reusable. The nonce is included in the Digest computation, so the server can rotate or validate it as part of replay control. Stronger replay protection can require short-lived or one-time nonces, with corresponding state and performance costs. A: `realm`, not `nonce`, labels the protection space. B: The `algorithm` parameter selects the digest algorithm; it is distinct from the challenge value. C: It identifies the nonce's role without claiming that every nonce policy prevents every replay.

Q4: Why is Digest authentication considered tricky in practice (select all)

Multi-Select
**Explanation:** RFC 7616 Section 3 defines the parameter-rich challenge/response operation, and Section 5 analyzes credential, server-authentication, and transport risks. Each selected statement describes a separate deployment burden or residual protection need. These trade-offs are why many current deployments prefer simpler token-based authentication inside a protected TLS channel. A: Parsing and generating the many quoted parameters, algorithm variants, nonce counts, and stale-nonce paths creates interoperability edge cases. B: A server can verify with H(A1), but compromise of that password-equivalent material can enable access within the realm. C: Digest does not give general confidentiality or integrity to the HTTP exchange, so TLS remains valuable. D: A counterfeit server can still present challenges; authenticating the server and channel remains necessary.

Q5: What is the parameter name for the server challenge value in Digest (one word)

Short Text
**Explanation:** The server-specified challenge value is called a **nonce**. It is opaque to the client and participates in the Digest response computation. A server can embed or track validity information in a nonce to restrict time, resource, client, or reuse conditions. A stale nonce can trigger a new challenge without asking for the password again. `cnonce` is a separate client-chosen value; it must not be confused with the server's `nonce`.

Q6: A correct statement about Digest and TLS is

Multiple Choice
**Explanation:** Digest authenticates a computed response. TLS protects the HTTP exchange as a channel and normally authenticates the server. TLS remains valuable because Digest does not provide general confidentiality or integrity for HTTP messages. TLS hides HTTP-level fields from passive observers, though network endpoints, timing, and traffic volume can remain observable. A: Not sending the raw password does not make request headers, response bodies, or most message fields confidential or tamper resistant. B: TLS protects the enclosing traffic, including the authentication exchange, while Digest supplies its own credential proof. C: TLS transports HTTP bytes securely; it does not rewrite the Digest input fields in a way that inherently invalidates the response.
