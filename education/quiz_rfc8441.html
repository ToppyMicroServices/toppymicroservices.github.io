Q1: In HTTP/2, WebSockets are bootstrapped primarily using

Multiple Choice
**Explanation:** **Terms:** extended CONNECT, HTTP/2 stream **Correct (B):** RFC 8441 bootstraps a WebSocket with the extended CONNECT mechanism on an HTTP/2 stream. **Options:** - A (incorrect): HTTP/2 does not use the HTTP/1.1 connection-wide Upgrade mechanism. - B (correct): Extended CONNECT adds a protocol pseudo-header and stream-scoped tunnel semantics. - C (incorrect): DNS service discovery does not establish a WebSocket over an HTTP/2 stream.

Q2: What does using WebSockets over HTTP/2 avoid compared to the HTTP/1.1 upgrade approach

Multiple Choice
**Explanation:** **Terms:** multiplexing, stream, TCP connection **Correct (C):** HTTP/2 can carry multiple streams on one connection, so each bootstrapped WebSocket does not inherently require a dedicated TCP connection. **Options:** - A (incorrect): RFC 8441 does not remove transport-security requirements. - B (incorrect): The exchange still uses HTTP semantics for setup and WebSocket semantics after a successful response. - C (correct): A WebSocket is associated with an HTTP/2 stream and can coexist with other streams on the connection.

Q3: Which value belongs in the :protocol pseudo-header when extended CONNECT bootstraps a WebSocket

Multiple Choice
**Explanation:** **Terms:** :protocol pseudo-header, extended CONNECT **Correct (A):** The client sends :protocol with the value websocket to identify the protocol intended for the stream. **Options:** - A (correct): websocket is the protocol value defined by RFC 8441 for this use. - B (incorrect): http names the surrounding protocol, not the WebSocket protocol being bootstrapped. - C (incorrect): TLS is not the :protocol value used to request WebSocket semantics.

Q4: Which are still relevant for WebSocket semantics when using HTTP/2 bootstrapping (select all)

Multi-Select
**Explanation:** **Correct (A,B,C):** The bootstrapping changes, but the security and application concerns remain **Options:** - A (correct): WebSocket frames and opcodes still define the data carried after a successful handshake. - B (correct): A browser still supplies Origin, and the server validates it according to its origin policy. - C (correct): The bootstrap does not decide which users or operations the application authorizes. - D (incorrect): HTTP/2 forbids the connection-specific Connection header and does not reuse the HTTP/1.1 Upgrade sequence.

Q5: A proxy only supports HTTP/2 and blocks Upgrade. What is a practical consequence for WebSockets

Multiple Choice
**Explanation:** **Correct (B):** Blocking HTTP/1.1 Upgrade does not establish whether RFC 8441 is available. The client must determine whether the HTTP/2 peer advertises extended CONNECT support. **Options:** - A (incorrect): An ordinary GET does not establish WebSocket framing and semantics. - B (correct): A peer that advertises the setting can accept the extended CONNECT bootstrap. - C (incorrect): Connection and Upgrade are connection-specific HTTP/1.1 fields and cannot be used this way in HTTP/2.

Q6: Which HTTP/2 setting must a server send with value 1 before a client uses extended CONNECT (exact name)

Short Text
**Explanation:** **Terms:** SETTINGS_ENABLE_CONNECT_PROTOCOL, peer opt-in **Correct:** SETTINGS_ENABLE_CONNECT_PROTOCOL. A server advertises value 1 to indicate support for extended CONNECT; a client must not send the :protocol pseudo-header before receiving that setting. **Related:** The setting enables the extended form of CONNECT. The request still uses the CONNECT method and supplies :protocol for the target application protocol.
