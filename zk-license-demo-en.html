Technical demo

Verify credential conditions
without revealing attribute values

Published October 4, 2026Updated October 10, 2026

日本語で読む

Toppy's public demo verifies ordinary-car driving entitlement and expiry conditions from a signed synthetic credential. It uses AnonCreds / anoncreds-rs for proof generation and cryptographic verification.1 Toppy's code matches the proven conditions to the verifier's request and manages one-time requests.

Match the proof to the stored request

The request requires can_drive_ordinary >= 1 and valid_until >= service_day from the same credential. The verifier configures the issuer's public key and credential definition. It does not trust a key supplied by the proof sender.

In the initial run with AnonCreds 0.2.3, passing the intended request to the cryptographic library did not reject proofs made for weaker conditions. The corrected verifier compares embedded attribute names, operators and thresholds with its stored request before cryptographic verification. Relabelling a weaker proof to match the requested bounds still fails the subsequent cryptographic check. Predicate matching implementation

Disclosed data and retained verifier state

The presentation does not disclose the name, address, date of birth, licence number or original expiry value. The verifier receives the proof, schema and credential-definition identifiers, request ID and proven conditions.

SQLite stores the request's expiry, audience, session and used status. The verifier checks this context and consumes a successful request within a transaction. A restart or concurrent submission cannot make that request reusable. Request state handling

Validation and scope

The October 4, 2026 validation record separates real AnonCreds integration tests from input, policy and state unit tests. It records rejection of weakened and tampered predicates and of another key using the same issuer ID, plus independent-process verification and replay rejection. The macOS record and Ubuntu CI results are public. Release checks fail if the real cryptographic library is unavailable.

This sample runs issuance, holding and verification on one machine with fictional credentials. Reading real driving licences, authenticating a person and checking suspension or cancellation are outside its scope. The CLI's session values do not authenticate a person.

This work was prompted by Park24's September 29, 2026 disclosure of leaked identity-document images. Deployment planning still involves decisions about the purpose, retention period and ownership of verification records. Japan's PPC guidelines provide further context on retention and management.
